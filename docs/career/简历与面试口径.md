# 简历与面试口径

> 用途：把「这个项目能怎么写、不能怎么写」固定下来。
> 原则只有一条：**写上去的每一句，都能在仓库里指到出处，并且经得起一个反问。**
> 数字来源全部在 `docs/report/` 与 `docs/acceptance/`，本文不新增任何数字。

---

## 一、一句话项目描述

> 校园限量名额发放平台（Java 21 / Spring Boot 3.3 / MySQL / Redis / RocketMQ）：**名额少、开放时刻固定、瞬时流量极高**，目标是让一次发放做到不超发、不少发、可对账。

## 二、四条可直接写进简历的 bullet

每条后面标了「出处」和「第一个反问怎么接」。反问接不住的那句，就别写。

### 1. 正确性

> **Lua 原子扣减 + 幂等键 + MQ 异步落库**：压测收尾 `55,328` 条请求对账 **`records = 幂等键 = issued + released`、`drift 0`**；`SIGKILL` 下 `stock 944,672 − 135,278 = 809,394` **精确相等**。

- 出处：报告 §二（正确性三件套）、README §1「B 块·正确性三道闸」
- 反问「`drift 0` 是在什么状态下读的？」→ **「B1 收尾、`pending=0` 时读的。B3 那段 `drift` 不能引用——中途停过 consumer，账本来就该不平，那组数据只用来测故障矩阵。」**
- 不要写成「任何情况下 `drift` 都为 0」——`+20` 那次就是反例，见第六节。

### 2. 性能归因

> **定位同步链路 `6,617 req/s` 的瓶颈在应用层而非 Redis**：绕过 HTTP / Spring / Lettuce 直打同一份 Lua 脚本为 **`83,635/s`（12.6 倍）**，**Redis 只占链路 RT 的 8%**。

- 出处：`docs/acceptance/2026-11-10/q4-bare-redis.md`、报告 §一 / §三
- 反问「12.6 倍说明 Redis 很快，那你还优化什么？」→ **「说明我该优化的不是 Redis。12.6 倍是 400 并发下的比值，裸 Redis 到 800 并发反而掉到 77,700——所以结论是‘瓶颈不在这一层’，不是‘Redis 更快’。」**

### 3. 归因方法论

> **用闭环 2×2 四臂（冷/热 × consumer 开/停，只翻一个开关）把两个吞吐数之间 13% 的差归因到消费者状态**：尾段配对 **`1.108` / `1.168`（几何 +13.7%）**，两对同向，并复现了此前那轮的 `10,766`（本轮 `10,898`，差 1.2%）。

- 出处：`docs/acceptance/2026-11-10/d7r-closedloop.md`、报告 §一
- 反问「13% 是精确值吗？」→ **「是下限。30 秒闭环没收敛，均值比尾段低 25%–35%，我只敢说‘主因是消费者状态、量级十几个点’。」**

### 4. 推翻自己（最值钱的一条）

> **发现并修正自己一个统计口径错误**：`3,845 / 48%` 的「不达标」是分母用了排空时长（`finMs 9,305`）而非 5 秒窗口的产物；60 秒开环稳态实际 **`7,821/s`**，NFR-6 结论从「差 48%」改为 **「差 2.2%，且缺的 1.90% 全在客户端（服务端零 5xx）」**。

- 出处：`docs/acceptance/2026-11-10/q7-steady-openloop.md`、报告 §四 4.1 #2、`自问自答.md` Q19
- 反问「改口之后到底达标没有？」→ **「还是不达标。NFR-2b 的口径是丢弃率 < 0.5%，实测 1.90%。但归因变了：不是‘系统扛不住’，是‘注入侧线程池队列满了’，请求没离开压测器。」**
- 这条的价值不在数字，在**「我能把自己写进报告的结论推翻，并且留下证据」**。

### 备选第 5 条（如果版面够）

> **测出容量是表规模的函数**：空表 3000 档 `thr 2,990`（P99 145ms），48 万行 / 60 秒稳态掉到 **`2,846`**（P99 5,565ms）；据此判定限流闸门 `3,000` 偏高，安全值取决于峰值表规模。

- 出处：`docs/acceptance/2026-11-11/rl-calibration.md`、`自问自答.md` Q20

## 三、三个不要写进简历的数字

| 不要写 | 为什么 | 要写就写 |
|---|---|---|
| 「支持 8000 QPS」 | 实测 7,821/s，且 1.90% 请求被客户端丢弃，按自家 NFR-2b（< 0.5%）**计为不达标** | 「8000 到达下服务端零 5xx，端到端差 2.2%」 |
| 「3000 QPS 限流」 | 闸门 3,000 **高于** 48 万行稳态容量 2,846，每秒 154 个请求注定排队——这是已知错配，不是能力 | 「闸门 3,000，实测空表可达 2,990、积压时仅 2,846」 |
| 「P99 145ms」 | 那是**5 秒窗口、空表**的产物；48 万行 60 秒稳态是 5,565ms。同一个指标跨窗口不可比 | 「P99 随表规模从 145ms 劣化到 5,565ms」 |

**共同点**：这三个都是「单值 + 不带条件」，一问条件就塌。凡是要写数字，前面加条件、后面加口径。

## 四、六条缺口的答法（被问到就这么说）

**要点：三条缺口分属三种性质，不要合成一句「没时间做」。**

| 缺口 | 性质 | 一句话答法 |
|---|---|---|
| **R-6** 补位队列 + 定向通知 | **主动砍**，非遗漏 | 「砍的。它和‘取消后能否重抢’耦合——补位要先定义谁有资格、优先级、超时怎么办，这三件事会反向改写取消状态机。状态机没定之前实现，只会留一段语义不闭合的代码。」 |
| **S-1** 活动浏览 / **S-5** 我的记录 | **计划阶段无落点** | 「需求到任务错配：它们都指向 D11，而 D11 只规划了管理端两个接口。事后判定不做——只读展示层，`quota_record` 已有 `studentId` 索引，补出来是半小时 CRUD，对不超发/可对账/高并发零增量。」 |
| **NFR-6** 8000 档 | **有能力但计不达标** | 「服务端零 5xx、处理 7,821/s，但 1.90% 被客户端丢弃；按 < 0.5% 口径就是不达标，我不改口径凑分。」 |
| **积压时释放 ≤ 1 秒** | **做不到** | 「无积压时 P99 是 0.5 秒（sweeper 周期 500ms）；积压 19 万条时，释放事件和落库挤在同一条 `cg_record` 队列，按 102–122 条/s 排队，延迟变成几十分钟。」 |
| **限流闸门 3,000** | **配置与容量错配**，待产品决策 | 「闸门高于实测容量 154。改不改取决于峰值期表会积多少行、持续多久——这是个产品输入，不是再扫几档能扫出来的常数。」 |
| **`+20` 那次漂移** | **不可回溯** | 「出现过一次 `drift +20`，机制查清了（DB 不回补、Redis 单边 INCR，方向是 fail-open），但触发点追不回来——因为取证协议是事后补的。所以文档里写的是‘方向不永远是 fail-closed’，不是‘已修复’。」 |

**一定会被问的一句**：「半小时的 CRUD 你现在补一下不行吗？」
**接住，别辩解**：「可以，半天内能补。不补不是难，是它证明不了什么。如果你要看，我下次带一版补上。」

## 五、讲这个项目的顺序（120 秒版）

1. **问题**：名额少、开放时刻固定、瞬时几千 QPS，核心是三件事——不超发、不少发、可对账。
2. **做法**：Lua 原子扣减（唯一扣减点）→ 幂等键（重放不重复发）→ MQ 异步落库（削峰）→ 对账（把账打平）。
3. **验证**：三条曲线找拐点、五类故障矩阵、开环两档线程判可用性边界。
4. **结论**：6.6k 的墙在应用层（裸 Redis 12.6 倍）；容量是表规模的函数（2,990 → 2,846）；8000 档差 2.2% 且缺的全在客户端。
5. **边界**：三条需求缺口 + 两处能力缺口，都在 `README` §10.2 与报告 §4.1。

第 4 步是主体，第 5 步是加分项——**主动说缺口的人，比等着被问出来的人可信**。

## 六、一条硬提醒：不要用「任何情况下」

这套系统里有三处**方向不是永远安全**的地方，写简历或口述时别用「保证」「任何情况下」这类词：

1. `drift` 的 fail-open 路径：`dbRemain == totalQuota` 时 DB 不再回补、Redis 仍 `INCR`，方向偏向「Redis 少扣」；
2. Redis `appendfsync everysec` 的 1 秒窗口：`SIGKILL` 测不出来，要宿主机断电才触发（**未覆盖**）；
3. 宿主机磁盘满会连 MySQL 一起不可用（**未验证**）。

正确说法是「**在已验证的五类故障下，账能打平；未验证的两类边界见 §10.3**」。
