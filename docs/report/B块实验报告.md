## 0. 口径与前提

七条，不先说明的话下面的数字都会被读歪：

1. **profile 一律 `bench`**（`NoLoggingImpl` + `com.campusslot: WARN`）。默认 profile 下
   `StdOutImpl` 会把每条 SQL 打到 stdout，吞吐不可比——这一条在 A 块验收时实测过。
2. **每轮前后 `reset` + `drain`**。`stat` 只有在 `pending=0` 时才能当账本读；否则 `records`
   小于成功数是"还没落库"，不是"丢了"。
   唯一例外：**B1 的 reset 从未生效**（压测器用 POST 打 `@GetMapping`，405 → 兜底 9001）。
   影响是 `hit` 列跨轮累积、探针余量没复位；**吞吐数字有效**（请求确实打进去了），不重跑。
3. **消费速率必须带积压量**：258 条/s（B5，积压 3 万）与 102–122 条/s（B3，积压 19 万）
   不矛盾——积压越深，同一行 `remain` 的行锁争用越重。
4. **B5 与 B6 共用同一次 60 秒压测**（3 万名额在同一次里打光），不是两次独立实验。
5. **B3 的 `drift` 数值不可引用**。它由 `ExpiredReleaseSweeper` 批量释放 19 万条超时 `LOCKED`
   造成，40 分钟里从 `+12` 走到 `−56` 再走到 `−31`，**方向都翻**。B3 只用 `stock` 的精确等式。
6. **r1 的硬截止是 2026-11-11 16:31**（`close_at`）。`reset` 会把它改写成 `now + 7 天`，
   每轮之后手工改回——这是复位接口的副作用，不是配置错误。
7. 主链路压测（B1–B6）在 **2026-11-09 18:00 前**完成；B7 的短写复现在 **18:26–18:31**
   （一次性旁路容器，不碰 r1）。**两代 B7 实验的数字不混用**：当日两次为 `588/1069`、
   `67,092,601`、`dbsize` 少 1 / 9；复现次为 `1657/7483`、`67,099,015`、少 6。
   r1 已复位为 `1000000 / 1000000 / 0 条`。

## 一、系统做了什么：同步链路 6.6k 封顶，异步链路 9.3k 仍在上升

同一台机器、同一梯度上的三条曲线：

| 并发 | ping（探针上限） | lua（纯 Redis 扣减） | claim/mq（完整链路） |
|---|---|---|---|
| 100 | 32,099 | 5,846 | 2,342 |
| 200 | **40,362** | 6,509 | 7,135 |
| 400 | 36,086 | **6,617** | 8,322 |
| 800 | 31,334 | 6,569 | **9,256** |

**三层的读数怎么解释**：

- **ping 是天花板，不是系统能力。** 40,362 @200 是探针（一个不碰 Redis 的 GET）能达到的极限，
  400/800 反而下降，是客户端线程与 GC 先到极限。它的作用是给下面两条曲线定上界。
- **lua 在 6.6k 附近封顶，且 400 与 800 几乎相同**（6,617 / 6,569，差 0.7%）——
  这是**同步链路**的饱和点：每个请求都在请求线程里等 Redis 脚本返回。
  与 D5 那轮同档的 6,700 差 **1.2%**，说明这个封顶值可复现，不是偶发。
- **这面墙在应用层，不在 Redis。** 2026-11-10 的 Q4 用旁路容器（`q4-redis`，同镜像、同 AOF、
  同 `noeviction`）直接把线上那份 `claim.lua` 交给 `redis-benchmark` 打 `EVALSHA`，
  **绕开 HTTP、Spring、Lettuce**：400 并发 **83,635/s**、800 并发 **77,700/s**，是 6,617 的 **12.6 倍**。
  同一并发下由吞吐反推的 RT：裸 Redis **4.78ms** vs `/api/dev/lua/claim` **60.4ms** ——
  **Redis 只占这条链路的 8%。** 证据：`docs/acceptance/2026-11-10/q4-bare-redis.md`。
  → 但"应用层"是个整体名词，本次**没有**继续拆到 MVC / 连接池中的哪一层；
  `application.yml:44` 的 `max-active: 64`（400 并发对 64 连接，排队系数 6.25）与这个差是同一量级，
  **但那只是算术上的巧合，不是观测，不能当结论用。**
- **claim/mq 一路涨到 9,256 @800，且没有出现拐点。** 与 D7 的主链路基线 **10,650** 差 **13%**。
  这 13% 在 B 块条件下是合理的：B1 每档只压 6 秒并在档间 `drain`，消费端有冷启动成分；
  D7 是长时间稳态。**所以报告里只能说"800 并发下 9,256，未观测到拐点"，不能叫峰值。**
  注意这句是**解释、不是对照**——没有重做一次与 D7 等长的稳态压测，所以 13% 只能写成
  "可能来自每档 6 秒 + 档间 drain 的冷启动"，不能说"已归因"。
  2026-11-10 的 Q7 补了一次 **60 秒开环稳态**（7,821/s，见 §四 4.1 #2），
  但它与 9,256 不是同一个量（开环到达 vs 闭环 800 并发），**没有替这一条提供对照**。

**结论**：MQ 解耦把请求线程与落库解耦，同步链路 6.6k 的墙被推到 9.3k 以上；
但代价是引入了一个新的同步依赖点（见 §三 B4）。

> 三组对照（裸 DB / +Redis / +MQ）的 A/B 数字属于 A 块，不在本文范围；
> 本文的三条曲线是"入口三档"，不是那三组。

## 二、并发正确的三道闸

先把判定顺序说清，否则错误码会被归错因：**Java 层先查名单**（`AsyncClaimService:148-151`，
`GET quota:roster:{rid}:{sid}`），命中后才进 `claim.lua`；**lua 内部的顺序是 stock → college**。
所以"没资格"由 `1005` 挡，"名额不够"由 `2001`（总名额）/ `2002`（学院）挡，三类错误码不会混。

### 闸一：总名额（Redis lua 原子扣减）

B3 的 `docker kill` 给了这条闸最硬的一个数：

```
944,672 − 135,278 = 809,394        AOF 恢复后实测 stock
```

**精确相等**。也就是说 SIGKILL 之后，已经 fsync 的 135,278 次扣减**一条没丢、一条没多**。
（`everysec` 的 1 秒窗口本次没覆盖到，见 §四。）

### 闸二：学院配额

第一轮 r2 的结论是错的，必须写清楚为什么：

- 第一轮 `total=80`、学院 `4×20=80`，两者相等 → 80 个成功后 `stock` 归零，
  剩下 120 个在 **lua 的第一行**就返回 `2001`，**根本没走到学院判定**。
  实测 `2001 拒 114 / 2002 拒 6`，这组数不是证据，是**反证**。
- 补测把 `total` 抬到 **200**（故意留 120 缺口），学院仍 `4×20=80`，200 个真实学号各打一次：

| 观测量 | 值 |
|---|---|
| `2001` | **0** |
| `2002` | **120**（= 200 − 80） |
| `stock` 剩余 | **120** |
| 逐学院（按 `quota_roster` 真实归属） | 各 50 请求 → **各 20 成功 / 各 30 个 2002** |
| 落库 `quota_record JOIN quota_roster` | 各 20 |
| `quota_college.remain` | 各 0 |

**这才是学院层的判据**：总名额有余量时，超出的请求全部被学院层精确拦下，既没穿透也没误伤。

> 一个方法论坑：按学号每 50 个切块统计会得到 21/22/17/20，看着像"分配不均"。
> 实际学院是按 `sid mod 4` 交错分配的，切块方式错了。证据里附了 `r2-roster-map.tsv`，
> 否则这张逐学院表无法自查。

### 闸三：名单（Java 层，不在 lua 里）

`AsyncClaimService:148-151` 在进 lua 之前先 `GET quota:roster:{rid}:{sid}`，取不到直接 `NOT_ELIGIBLE(1005)`。
所以名单判定**根本不进 Redis 脚本**——它挡住的是"没资格的人"，不是"名额不够"。

故障矩阵里这一条要单列，否则会误判：

| 删掉的 key | 返回码 | 说明 |
|---|---|---|
| `quota:stock:{rid}` | **9005** | 缓存缺失，直接拒 |
| `quota:college:{rid}:{code}` | **9005** | 同码，只能靠日志区分 |
| `quota:roster:{rid}:{sid}` | **1005** | 名单未命中 |
| `quota:res:{rid}` | 无错误 | 5 秒 TTL + 按需写入，删了只是回源重填 |

> `quota:res` 那条曾经写错过两次：先是名字写成 `quota:meta:*`（不存在），
> 后是把结论写成"证明缓存层对正确性无影响"。实际它大部分时间本来就不在（TTL 5 秒），
> 删它只能说明"删了不报错"，不能当"缓存无关"的证明。

### 闸的端到端行为

- **幂等**：同一学号连打 100 次（dup 模式）→ 落库 **1 条记录**，`quota_college.remain` 精确 `−1`。
- **并发**：200 个真实学号各打一次（burst 模式，同一次补测）→ 成功 **80**、`2002` 拒 **120**、
  `2001` **0**；`drain` 后四院 `quota_college.remain` 与记录计数**逐学院相等**（各 20）。

### 正确性三件套

| 判据 | 结果 | 依据 |
|---|---|---|
| 超卖 | **0** | B1 收尾 `55,328` 记录 = `55,328` 幂等键、`drift 0`（**这一条读自 B1 的收尾，`pending=0`**；B3 那段 `drift` 不可引用，见口径 5）；B3 的 `stock` 在 SIGKILL 下精确相等 |
| 重复 | **0** | dup 100 次 → 1 条记录；全程 `idemKeys = records` |
| 对账差异 | **0** | `drain` 后 `dbRemain = redisRemain`、`balanced=true`；学院层逐院相等 |

> 注意第三条只在 `pending = 0` 时可读（口径第 2 条）。B5 停消费端那段 `balanced=false` 是预期形态。

### 消息不丢

B5 停掉消费端 60 秒再拉起：

| 观测 | 值 |
|---|---|
| `pending` 峰值 | **30,000 = 成功数**（严格相等） |
| `drift` | `−30000 = −pending`（预期形态，不是故障） |
| 追平耗时 | **116 秒**（≈ 258 条/s） |
| 追平曲线 | `records` 单调增长到 30,000，`pending` 归 0，**没有"恢复瞬间归零"** |

最后一条是判据：如果恢复后 `pending` 立刻归零，说明 broker 的位点把消息跳过了——
那比"追平慢"严重得多。实测是正常追平。

> **"严格相等"是必然而非巧合**：这一轮 r1 被 `reset` 到 3 万名额（口径 4），成功数上限就是 30,000，
> 打光之后 `pending` 不可能再涨。所以这条判据真正测的是"**峰值 = 成功数**"——
> 若有消息在途丢失，`pending` 会小于成功数；若有重复投递，会大于。

> 停消费端期间 `stat` 必然 `balanced=false`（`idemKeys > records`、`pending > 0`）。
> 这是**预期形态**，不是链路坏了。报告里必须前置说明，否则截图会被误读。

### 入口到底碰不碰 DB

停消费端后用 `SHOW GLOBAL STATUS LIKE 'Questions'` 数入口的 DB 访问：

| 观测 | 值 |
|---|---|
| 空转基线（无压测） | 3.33 次/s（100 次 / 30 秒） |
| 压测 60 秒（739,248 个请求） | 2,410 次，扣基线 ≈ **2,207** → **37 次/s** |
| 占请求数比例 | **0.30%** |
| 重填周期 | **5.0 秒**（与 `meta-cache-ttl-ms: 5000` 一致，5Hz 采样粒度 0.2s） |
| 单次脉冲的回源请求数 | **93 @100 并发 / 158 @200 并发** |

**结论**：入口的 DB 依赖只有 `metaCache` 回源一处，量级 0.3%——所以 B1 的曲线没有被惊群污染。

但 93/158 这个规模值得单独记一笔：`loadFromDb` 一次两条 SQL，所以一次脉冲是
**近百个请求同时回源**。按"1–2ms 回源窗口 × QPS"推出来是 7–14，差一个数量级；
实测与**在途请求数（`QPS × RT`）同量级**（A 组 `12,682×7ms=89` 对 93，B 组 `13,386×14ms=187` 对 158，
后者低 16%）。也就是说回源窗口是**一整个请求的处理时间**，不是那 1–2ms 的 DB 往返。
**这不是连接池封顶**：若是 64 个 Hikari 连接封顶，两档会卡在同一个数，而实测 93 → 158。

## 三、故障下的表现（五类）

| # | 故障 | 注入方式 | 观测 | 影响 | 恢复 |
|---|---|---|---|---|---|
| 1 | Redis 进程被杀 | `docker kill`（SIGKILL），压测中 | ok 135,278，`stock = 809,394 = 944,672 − 135,278` | 已 fsync 的扣减**零丢失**；1 秒窗口未覆盖 | 重启后 AOF 完整恢复 |
| 2 | MQ 干净停机 | `mqshutdown broker`（T+4s） | ok 33,158 / `9003` 拒 **116,635（78%）**；p99 **471ms** | **78% 请求被拒**，不是吞吐塌陷 | `broker-a` 重新可见 **67 秒**（首测 76s） |
| 3 | 消费端停 60 秒 | `Stop-Process` 杀 consumer | `pending` 峰值 = 30,000；无位点跳过 | 只积压，不丢 | **116 秒**追平 |
| 4 | 磁盘写满 | 旁路 64MB tmpfs + 灌 1KB × 20 万 | `MISCONF … No space left on device`，`SET`/`INCR` 都拒，读正常 | **可用性**（→ 9001），不是正确性 | 见下 |
| 5 | 崩溃后重启 | `pkill -9` + 原地拉起 | 加载无 warning、AOF 长度不变、`dbsize` 少 **1 / 9**（当日两次）与 **6**（复现次） | 丢 kill 瞬间未 flush 的命令 | 正常加载 |

> #5 是 **3 次独立观测**，不是 1 次：当日 `b7-aof-restart.md` 两次（少 1、少 9），
> 18:26–18:31 的复现 `b7-shortwrite-repro.md` 一次（少 6）。三者机制相同、数字不同，
> **不可合并成一个区间**，引用时要点明是哪一次。

### B4：那 10 分钟不是 RocketMQ 慢，是 PID1 不转发信号

11-05 那次 `docker stop` 恢复花了 10 分钟。这次查清了机制：`cs-broker` 的 **PID1 是 `sh mqbroker`**，
不是 JVM。`sh` 不转发信号，`docker stop` 的 SIGTERM 到不了 Java，10 秒宽限期后直接 SIGKILL——
于是下次启动要重建 ConsumeQueue。

`mqshutdown` 走的是另一条路：脚本里 `ps ax | grep BrokerStartup | awk '{print $1}'` 然后 kill 那个 java PID，
让 JVM 自己 flush 再退。实测 **67 秒**（首测 76 秒）恢复，对照 10 分钟。

**所以"强杀导致重建"这个判断成立，而且机制讲得清。** 但如果这次也是 10 分钟，
结论就该改成"恢复耗时与退出方式无关，是 ConsumeQueue 恢复本身"——两个走向都是有效结论。

### B4：没有出现"每请求 3 秒"

`RocketMqProducer` 设置了 `setRequestTimeout(3000)`，`producer.send()` 是同步调用，
原预期是 broker 挂掉后每个请求阻塞 3 秒、吞吐塌到 ~66/s。**实测不是**：

| 观测 | 值 |
|---|---|
| 总请求 | 149,793 |
| 成功 / 被拒 | 33,158 / 116,635（78% 答 `9003`） |
| 吞吐 | 2,495 req/s（**高于** B1 同并发档的 2,342） |
| p50 / p95 / p99 | 33 / 49 / **471ms** |
| 配额回补 | 已消耗 33,158 = ok 33,158（**精确**） |

原因：broker 进程一死，TCP 连接被 RST，`send()` 立刻抛错（~40ms）。
**3 秒超时只在"连接还在、对端不回包"时生效**，本次窗口没覆盖到那个分支（见 §四）。

**那为什么还有 33,158 个成功（22%）？** 因为停机不是 60 秒全程：`mqshutdown` 在 T+4s 发出，
实际 SIGTERM 落在 T+8s、容器退出约 T+13s（`b4-timeline.txt`），前面这 13 秒是正常服务。
按吞吐反推也吻合：`33,158 ÷ 13s ≈ 2,550/s`、`116,635 ÷ 47s ≈ 2,480/s`，两段之和正是 60 秒。
**所以 B4 的正确读法是「13 秒正常 + 47 秒全拒」，不是「78% 的请求随机失败」。**

顺带纠正两处：`MQ_UNAVAILABLE` 是 **9003**（不是 1601）；给 B4 加"配额封顶"是无效动作——
发送失败会走 `compensate()`（`INCR stock` + 删幂等键），**停机窗口内一条消息都不产生**。

### B7：磁盘满时拒写，不虚高；但重启后有个"假成功"窗口

**拒写，不是静默接收。** 写命令返回 `MISCONF Errors writing to the AOF file: No space left on device`，
`SET`/`INCR` 都拒；读正常，`dbsize` 保留。所以磁盘满的风险是**可用性**
（扣减失败 → EVAL 抛错 → 9001），不是**正确性**（超发）。

**AOF 尾部是完整的。** 这一点曾经写错过两次，现在的结论有定量证据。

> **两代实验的数字不能混用**：当日 `b7-aof-restart.md` 的两次重启只量了 `dbsize`，
> 短写日志是 `588/1069`、incr 为 `67,092,601`、少 1 / 9 条；
> 下面这组更干净的定量（`1657/7483`、`67,099,015`、少 6 条、`size mod 1069`）
> 来自 18:26–18:31 的复现 `b7-shortwrite-repro.md`——它把崩溃前后的长度、日志全文、
> 尾部字节一次测全。**同一句话里不要同时引两代的数**。

**两条主证据（不依赖"每条命令等长"这个前提）：**

- **崩溃后 incr 文件以 `\r\n` 结尾**。一条被截断的 RESP 命令不可能以 `\r\n` 收尾——残缺文件的
  末尾一定停在参数中间。这是"尾部完整"的**直接观测**。
- **加载日志零 warning**。构造实验（`b7-aof-truncation.md`）已经证明：尾部残缺时默认配置
  **必然**打三行 warning（`short read` / `Truncating ... at offset N` / `loaded anyway`）并
  `ftruncate`。这里一行都没有 → 加载器压根没进截断分支。

**佐证（依赖 `-d 1024` 的定长假设）：** 短写日志 `Short write (nwritten=1657, expected=7483)`，
`7483 = 7 × 1069`、`1657 = 1069 + 588`，落点在第 2 条命令中间；
`67,099,015 − 23 = 62,768 × 1069`，`size mod 1069 = 23`。
这组算术与"尾部完整"一致，但它的前提是每条 `SET` 恰好 1069 字节——所以只作佐证，不作主证据。

**机制**：部分写之后 Redis 用 `sdsrange` 保留缓冲区剩余，下一次 flush 接着写。
**短写只是把一次 write 拆成两次，不产生残缺 AOF**；真正丢的是 kill 瞬间还在 buffer 里的新命令
（复现次 `dbsize` 少 6 条）。所以"有短写、无警告、长度不变"不矛盾——**文件根本没缺**。
上一版用"481 字节从未进入文件"去解释它，等于用一个必然导致 `short read` 的假设去解释
"没有 `short read`"，已废弃。

**`aof-load-truncated` 的作用是另一件事，构造实验测的**：往 AOF 尾部追加半条 `SET` 后，
默认 `yes` 会打三行 warning（`short read` / `Truncating ... at offset 110` / `loaded anyway`）、
把文件 `ftruncate` 回上一命令边界、然后正常启动；设 `no` 则 **`exit 1` 拒绝启动**，
提示 `redis-check-aof --fix`。当日那两次重启**没有触发它**（长度不变、无 warning），
因为尾部本来就完整。

**重启后能写 ≠ 磁盘恢复。** 重启把 `aof_last_write_status` 复位为 `ok`，`/data` 可用仍是 0KB，
但复现次实测前 2 条 1KB 写入都返回 `OK`，第 3 条起才 `MISCONF`——命令追加到 `aof_buf` 就返回，
flush 在其后，状态位只在 flush 失败后才置 `err`。
**存在 1–2 条的假成功窗口**：返回 OK 但没落盘，再重启就丢。运维上不能拿"写成功"当空间已恢复的证据。

**附带**：磁盘满时 SIGTERM 会因"存最终 RDB 失败"而**拒绝退出**，`docker restart` 拖满 10 秒宽限期
再 SIGKILL（实测 10.7s）。磁盘满时"优雅停机"退化成硬杀，停机预算要按 10s + SIGKILL 算。

## 四、边界：三处设计上不满足、三处覆盖不到、两处行为特征

分三类写，因为性质完全不同：**不满足是"该做没做"，覆盖不到是"本机做不了"，行为特征是"就这样、不是缺陷"**。
混在一起会被读成"要么全做了、要么全没做"。

### 4.1 三处设计上不满足（需求层面的缺口，不是测试没跑到）

| # | 需求 | 现状 | 证据 |
|---|---|---|---|
| 1 | **R-6：退掉的名额给排队同学 + 定向通知** | **未实现**。`quota_backfill_queue` 表建了但是空的；`quota_backfill` topic 只登记在 producer 的 `setTopics` 里（为满足"发之前必须声明"这一约束），**既没有发送点、也没有消费者**。释放的名额回到余量池，下一个来抢的人正常拿到，但**不会主动通知排队的人** | README §6 |
| 2 | **NFR-6：8000 QPS 端到端** | **差 2.2%**。60 秒开环稳态处理 **7,821/s**（2048 线程）/ 7,371/s（768 线程），服务端零 5xx；但 8000 到达时仍有 **1.90%** 请求被客户端丢弃（`rej=9,106`），按 NFR-2b 口径（< 0.5%）**不达标**。<br>**旧的"3,845/s（48%）"作废**：那是把 D5 的 9.3 秒排空尾巴摊进 5 秒分母，同一行的 `thr` 本来就是 **7,154**。**B1 的 9,256 同样不能拿来说事**——那是闭环 800 并发，与开环到达是两个量 | `docs/acceptance/2026-11-10/q7-steady-openloop.md` |
| 3 | **积压时释放延迟 ≤ 1 秒** | **做不到**。稳态（无积压）P99 在 **0.5s** 量级，由 500ms 的 sweeper 周期决定；但**积压 19 万条时，新过期记录的释放延迟是几十分钟**——释放事件与落库走同一条 `cg_record` 队列，按 102–122 条/s 排队 | LOGBOOK §7 / 本文 §二 消费速率 |

这三条都是"设计上就没做到"，不是"没测"。写在这里的理由很简单：**"能不能上线"这个问题，第一条一定问到这里。**

### 4.2 三处覆盖不到（想测，本机测不了）

| # | 边界 | 为什么覆盖不到 | 报告口径 |
|---|---|---|---|
| 1 | `appendfsync everysec` 的 1 秒窗口 | `docker kill` 只杀进程，OS 的 page cache 还在，AOF 一定完整（`944,672 − 135,278` 精确相等就是证据）。要丢数据得宿主机断电 / OS 崩溃 | **"SIGKILL 下零丢失；1 秒窗口需断电才能测，未覆盖"** |
| 2 | 宿主机磁盘满 → MySQL 一起不可用 | `cs-redis` 的 `/data` 和 MySQL 在**同一块 `ext4.vhdx`**，真打满会连 Windows 一起卡死，连删文件的命令都进不去；rdb 只保 Redis，MySQL 侧没有对应备份 | **"未验证"**，不写"测过没事" |
| 3 | B4 的 `setRequestTimeout(3000)` 分支 | broker 进程一死 TCP 就 RST，`send` 立刻抛错。3 秒只在"连接还在、对端不回包"时出现（比如 broker 假死、网络黑洞） | **"78% 被拒，未观测到 3 秒阻塞；3 秒分支未覆盖"** |

### 4.3 两处行为特征（不是缺陷，但会被问）

- **5 秒周期的惊群**：`metaCache` 没有 single-flight，key 过期那一刻有 ~93–158 个请求同时回源。
  量级只占 0.3%，不影响正确性，但它是**唯一**的 DB 依赖点。
- **消费速率随积压下降**：258 条/s（积压 3 万）与 102–122 条/s（积压 19 万）。
  根因是同一行 `remain` 的行锁争用 + 通知写入。引用任何一个速率都必须带积压量。

## 五、下一步（按收益排序）

§四 4.1 的三处设计缺口里，**R-6 补位队列不在本期范围**（要与"取消后不可重抢"一起重新设计），
另外两处（NFR-6、释放延迟）**指向同一个地方：消费侧吞吐**——所以下面第 2 条是主线。

1. **`metaCache` 加 single-flight**。5 秒一次的惊群是当前唯一的缓存层缺陷，
   加一个 `CompletableFuture` 级别的去重即可，改造成本约 20 行。
2. **800 并发以上继续找拐点**。claim/mq 到 800 仍在上升，天花板未知；
   找到拐点才能给容量结论，现在还只能说"≥ 9,256"。
3. **`CLOSED` 状态没有写入方**。全仓没有把 `PUBLISHED` 改成 `CLOSED` 的代码，
   R-7 属于"有实现、无触发"；当前靠 `ResourceMeta.isOpen()`（`now > close_at` 拒绝申领）
   和 README §3.5 的手工关账兜住。
4. **学院维度是"名单上写的"，不是"发的时候扣的"**。`quota_record` 没存 `college_code`，
   按学院报数必须 JOIN `quota_roster`。要支持"发的时候按学院统计"，得加一列。

> **本报告不提供容量结论。** 三个原因叠在一起：没有观测到拐点（闭环只能给下限 `≥ 9,256`）、
> 压测端与被测端同机（绝对值换机器不成立）、长时间稳态仍未做够（Q7 补了 60 秒开环，
> 但内存 / 连接 / GC 的长周期行为依然未观测）。
> **不要把 9,256（闭环）或 7,821（开环）当容量上限引用**——它们是本机上两个不同边界条件下的观测值，
> 不是系统的天花板。两者差 18.3%（闭环更高），原因是闭环客户端会等、到达强度低于 8000 持续打，
> **这一条至今是解释、不是对照**。
