## 3. 口径与前提（报告里必须前置声明）

1. **profile 一律 `bench`**（`NoLoggingImpl` + `com.campusslot: WARN`）。用默认 profile 时
   `StdOutImpl` 会把每条 SQL 打到 stdout，吞吐数字不可比。
2. **每轮前后都 `reset` + `drain`**：`stat` 只有在 `pending=0` 时才能当账本读，否则
   `records` 小于成功数是"还没落库"，不是"丢了"。
   唯一例外是 **B1 的 reset 从未生效**（hammer 用 POST 打 `@GetMapping`，405）——
   B1 的 `hit` 列不可信、探针余量跨轮累积，但**吞吐数字有效**（请求确实打进去了），不重跑。
3. **消费速率必须带积压量**：258 条/s（B5，积压 3 万）与 102–122 条/s（B3，积压 19 万）
   不矛盾——积压越深，同一行 `remain` 的行锁争用越重。
4. **B5 与 B6 共用同一次 61 秒压测**（30,000 名额在同一次里打光），不是两次独立实验。
5. **B3 的 `drift` 数值不可引用**：那是 `ExpiredReleaseSweeper` 批量释放 19 万条超时 LOCKED
   造成的，40 分钟里从 +12 走到 −56 再走到 −31，方向都翻。B3 只用 `stock` 的精确等式。
6. **r1 的硬截止是 2026-11-11 16:31**（`close_at`）。`reset` 会把它推到 +7 天，每轮之后手工改回。
7. 主链路压测（B1–B6）在 **2026-11-09 18:00 前**完成；B7 的短写复现在 **18:26–18:31**（一次性旁路容器）。
   **两代 B7 的数字不混用**：当日 `588/1069`、`67,092,601`、少 1 / 9；复现 `1657/7483`、`67,099,015`、少 6。

## 4. 三处"设计上不满足"（不是没做，是做不了）

| 项 | 为什么覆盖不到 | 报告怎么写 |
|---|---|---|
| `appendfsync everysec` 的 1 秒窗口 | `docker kill` 只杀进程，page cache 还在，AOF 一定完整（B3 的 `944,672 − 135,278` 精确相等就是证据）；要丢数据得宿主机断电 | "SIGKILL 下零丢失；1 秒窗口需断电才能测，未覆盖" |
| 宿主机磁盘满 → MySQL 一起不可用 | `cs-redis` 与 MySQL 共用一块 `ext4.vhdx`，真打满连删文件的命令都进不去，rdb 只保 Redis | "未验证"，不写"测过没事" |
| B4 的 `setRequestTimeout(3000)` | broker 进程一死 TCP 就 RST，`send` 立刻抛错；3 秒只在"连接还在、对端不回包"时出现 | "78% 被拒，未观测到 3 秒阻塞；3 秒分支未覆盖" |
