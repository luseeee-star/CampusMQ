## 3. 口径与前提（报告里必须前置声明）

1. **profile 一律 `bench`**（`NoLoggingImpl` + `com.campusslot: WARN`）。用默认 profile 时
   `StdOutImpl` 会把每条 SQL 打到 stdout，吞吐数字不可比。
2. **每轮前后都 `reset` + `drain`**：`stat` 只有在 `pending=0` 时才能当账本读，否则
   `records` 小于成功数是"还没落库"，不是"丢了"。
   唯一例外是 ~~B1 的 reset 从未生效~~ → **2026-11-10 更正：仅 ping 档的 reset 405**。
   两个 reset 方法不同：`/ping/reset` 是 `@GetMapping`（只清 `hits`），`/api/claim/dev/reset` 是 `@PostMapping`（真复位）。
   hammer 当时一律 POST，所以只有 ping 档得 405；**lua 与 claim/mq 档的复位一直生效，每档满额度起跑**。
   受影响范围只有 ping 档的 `hit` 列（跨轮累积、不可信）；**三条曲线吞吐数字全部有效**，不重跑。
3. **消费速率必须带积压量**：258 条/s（B5，积压 3 万）与 102–122 条/s（B3，积压 19 万）
   不矛盾——积压越深，同一行 `remain` 的行锁争用越重。
4. **B5 与 B6 共用同一次 61 秒压测**（30,000 名额在同一次里打光），不是两次独立实验。
5. **B3 的 `drift` 数值不可引用**：那是 `ExpiredReleaseSweeper` 批量释放 19 万条超时 LOCKED
   造成的，40 分钟里从 +12 走到 −56 再走到 −31，方向都翻。B3 只用 `stock` 的精确等式。
6. **r1 的硬截止是 2026-11-11 16:31**（`close_at`）。`reset` 会把它推到 +7 天，每轮之后手工改回。
7. 主链路压测（B1–B6）在 **2026-11-09 18:00 前**完成；B7 的短写复现在 **18:26–18:31**（一次性旁路容器）。
   **两代 B7 的数字不混用**：当日 `588/1069`、`67,092,601`、少 1 / 9；复现 `1657/7483`、`67,099,015`、少 6。

## 4. 三类边界：设计上不满足（没做） / 覆盖不到（做不了） / 行为特征（就这样）

**这个分节标题原来写反了**：旧标题是「三处"设计上不满足"（不是没做，是做不了）」，
而下面表里三条全是**覆盖不到**，真正的三处设计缺口（R-6 / NFR-6 / 释放延迟）一条没提。
把"没做"写成"做不了"，等于把交付缺口包装成实验限制——这是 C 块最容易踩的一脚。

### 4.1 设计上不满足（需求要求了、没做）

| 项 | 现状 | 证据 |
|---|---|---|
| **R-6 补位队列 + 定向通知** | 未实现：`quota_backfill_queue` 表空、`quota_backfill` topic 无发送点无消费者；释放名额回余量池，不通知排队的人 | README §6 |
| **NFR-6 的 8000 QPS 端到端** | **端到端差 2.2%**（不是"48% 不达标"）：60 秒开环处理 **7,821/s**（2048 线程）/ 7,371/s（768 线程），服务端零 5xx；缺的 **1.90%** 全是客户端 `rej`（`err/full/other/limited` 全 0，`rej` 不产生 HTTP 事务），所以**注入侧与系统侧当轮无法归因**（那 3.1 秒停滞的层位未定位），本档只能判「未观测到服务端边界」，**"差 2.2%" 与 "1.90%" 是同一批 9,106 条**。**旧的 3,845/48% 作废**——那是把 9.3 秒排空尾巴摊进 5 秒分母，同一行 `thr` 本来就是 7,154 | `2026-11-10/q7-steady-openloop.md` §六、§十 |
| **积压时释放延迟 ≤ 1 秒** | 做不到：稳态 P99 ~**0.5s**（500ms 周期），积压 19 万时**几十分钟**（与落库共用 `cg_record`，102–122 条/s） | LOGBOOK §7 |

### 4.2 覆盖不到（想测、本机测不了）

| 项 | 为什么覆盖不到 | 报告怎么写 |
|---|---|---|
| `appendfsync everysec` 的 1 秒窗口 | `docker kill` 只杀进程，page cache 还在，AOF 一定完整（B3 的 `944,672 − 135,278` 精确相等就是证据）；要丢数据得宿主机断电 | "SIGKILL 下零丢失；1 秒窗口需断电才能测，未覆盖" |
| 宿主机磁盘满 → MySQL 一起不可用 | `cs-redis` 与 MySQL 共用一块 `ext4.vhdx`，真打满连删文件的命令都进不去，rdb 只保 Redis | "未验证"，不写"测过没事" |
| B4 的 `setRequestTimeout(3000)` | broker 进程一死 TCP 就 RST，`send` 立刻抛错；3 秒只在"连接还在、对端不回包"时出现 | "78% 被拒，未观测到 3 秒阻塞；3 秒分支未覆盖" |

### 4.3 行为特征（不是缺陷）

- 5 秒周期的惊群：每次 **93 @100 / 158 @200** 个请求同时回源，占 0.30%，不影响正确性。
- 消费速率随积压下降：**258 条/s**（积压 3 万）→ **102–122 条/s**（积压 19 万）。
