## 一处日志口径要记住：`INFO` 挡不住 SQL

`application.yml:52` 是 `mybatis-plus.configuration.log-impl: StdOutImpl`——它**绕过 logback 直写 stdout**，
所以 `--logging.level.com.campusslot=INFO` 之后 SQL 仍然照打（日志里那些没有时间戳的行就是它）。
证据日志因此做了二次过滤：只留带 `HH:mm:ss.SSS` 的行。

**B1 不能只"降 INFO"**，必须带 `--spring.profiles.active=bench`：`application-bench.yml` 里是
`NoLoggingImpl` + `com.campusslot: WARN`，那才是 D2 那次「295 req/s vs 关掉日志后」的同一套口径。
只降 INFO 会让 B1 的吞吐里混进 stdout I/O，和 D5/D7 基线不可比。

## 两件比"没验过"更要紧的事

**1. `writeFinalReport` 不仅没有入口，生产上根本不会被触发。**
全仓 grep `CLOSED` 只有四处：`ReconcileJob` 的判定、枚举、`ResourceAdminService:339` 的"不许重发布"注释、实体注释。
**没有任何代码会把活动从 `PUBLISHED` 改成 `CLOSED`**——没有关账 job，也没有关闭接口。所以：
- 本次是手工 `UPDATE quota_resource SET status='CLOSED'` 造出来的场景，验的是"分支写对了"，不是"链路通了"；
- R-7「每次发放留一份可归档报表」目前的准确说法是**有实现、无触发**。
两条路选一条：把它定成操作纪律（演示/归档时手工 UPDATE，写进 README），或在 B 块后补一个关账 job
（扫 `close_at < now AND status='PUBLISHED'` → `CLOSED`，20 行左右，但要占一次重启和一轮回归）。
**已定（2026-11-05 17:45）：两条都要，但分先后——现在只写操作纪律（SQL 与三条判据见 `README.md` §3.5 末「手工关账」），
关账 job 排到 B 块之后、C 块写材料之前，`campusslot.close.enabled` 默认 false，宽限 60 分钟，条件更新，不碰 Redis。**
不在 B1 前夜动代码：它只是归档触发器（`close_at` 一过 `isOpen()` 自己就关了），不值得换一次重启 + 回归。

**2. 报表行数 ≠ 发放次数。**
`ReconcileService:133` 的 `writeReport` 是无条件调用的（没有 `hasReport` 判断，幂等只做在 `writeFinalReport` 里）。
持续差异会**每个周期写一行**。所以引用报表时只能说"有差异的活动每周期一份快照，取 `generated_at` 最新的一份"，
不能写成"每次发放一份"——后者是 R-7 的原始措辞，和实现对不上。
