# Q4 · 6,617 是 Redis 的墙还是应用层的墙

> 2026-11-10 13:54。旁路容器 `q4-redis`，**不碰 `cs-redis`、不碰 r1 的任何 key**。
> 原始输出：`q4-redis-raw.txt`。

## 一、为什么必须旁路

B1 的 `lua` 曲线走的是 `/api/dev/lua/claim`——HTTP → Tomcat → Lettuce → `claim.lua`。
那个 6,617 里混着三层：Spring MVC/Jackson、连接池排队、Redis 本身。
在同一个 JVM 里再怎么调，都无法把这三层拆开；而"改一行代码重启再比"会被冷启动差异淹没
（`ClaimDevController:73` 那段注释已经记过这个坑：0.62 的冷启动系数与 40% 的效应同量级）。

所以换一个方向：**把脚本搬到另一个 Redis 上，用 Redis 自带的压测器直接打 EVALSHA**，
让应用层完全不在链路上。剩下的数就是"Redis 自己能做到多少"。

## 二、实验设置

| 项 | 值 | 为什么这么定 |
|---|---|---|
| 镜像 | `redis:7.2`（容器内 `7.2.17`） | 与 `cs-redis` 同一主版本 |
| 持久化 | `--appendonly yes` | **必须与 `cs-redis` 一致**。关掉 AOF 等于换了一个更快的系统，比出来的是配置差不是层次差 |
| 内存策略 | `--maxmemory 1gb --maxmemory-policy noeviction` | 同 `cs-redis`，避免淘汰干扰 |
| 脚本 | 直接 `docker cp` 线上那份 `claim.lua`，`SCRIPT LOAD` 得 `e45b1a42…` | 一个字都没改 |
| 单 key | `quota:stock:9001 = 20,000,000` | 保证 60 万次 DECR 打不到 0，否则中途会变成走 `stock <= 0` 的短路分支 |
| idem 键 | `quota:idem:9001:__rand_int__`，`-r 100000000` | **这是本次实验最容易做错的一处**，见下 |
| 学院配额 | 传 dummy key + `ARGV[2]='0'` | 关掉学院分支，与 B1 的 lua 曲线口径一致 |
| 并发 | 400 / 800 | 与 B1 的两档对齐 |

**idem 键为什么必须打散**：`claim.lua` 第一行就是 `EXISTS idemKey`，命中即 `return {-2, first}`。
如果所有请求用同一个 idem 键，除第一次外全部在第二行返回，
测到的就是"一次 EXISTS 有多快"——那个数会比真实路径高一个数量级，而且曲线同样漂亮。
所以用 `-r 100000000` 让每次请求的学生号随机。

**验证它真的生效了**（不是靠信任）：先跑 5,000 次，再数键——
`quota:idem:9001:*` 恰好 **5,001** 个。占位符生效。

## 三、结果

| 并发 | 吞吐 | p50 | p95 | p99 |
|---|---|---|---|---|
| 400 | **83,635 /s** | 3.919 ms | 6.207 ms | 7.543 ms |
| 800 | **77,700 /s** | 8.471 ms | 13.879 ms | 17.327 ms |

`INFO commandstats`（60.5 万次 EVALSHA 累计）：

```
cmdstat_evalsha  calls=605001  usec_per_call=4.64
cmdstat_exists   calls=605001  usec_per_call=0.44
cmdstat_get      calls=605001  usec_per_call=0.27
cmdstat_decr     calls=603140  usec_per_call=0.25
cmdstat_set      calls=603141  usec_per_call=0.81
```

**一处自洽性校验**：EVALSHA 共 605,001 次，DECR 只有 603,140 次，差 **1,861**。
这 1,861 次就是 `EXISTS` 命中的早返回。按生日问题算，池子 1e8、抽 6.05e5 次，
期望碰撞数 `N²/(2P) = 1800`——与实测 1,861 吻合（差 3.4%）。
这条不是装饰：它同时证明了占位符真的随机、脚本真的走了完整路径、且碰撞量级与模型一致。
如果占位符失效，这个差值会是 60 万而不是 1,861。

## 四、判读（三分支，跑之前就写死的那张表）

| 裸 Redis | 结论 | 实测 83,635 / 77,700 |
|---|---|---|
| ≈ 6.6k | 墙在 Redis 单 key 串行化，关账 | — |
| ≥ 20k | 墙在应用层 | ✅ **命中** |
| 中间 | 两层叠加 | — |

**结论：6,617 不是 Redis 的墙，是应用层的墙。差 12.6 倍（83,635 ÷ 6,617）。**

把同一个并发下的延迟摆在一起看更直接：

| 链路 | 并发 400 的吞吐 | 由吞吐反推的 RT |
|---|---|---|
| 裸 Redis（本次） | 83,635 /s | 4.78 ms |
| `/api/dev/lua/claim`（B1） | 6,617 /s | **60.4 ms** |

同一个并发、同一个脚本，RT 差了 55.6 ms。**Redis 侧只占这条链路的 8%。**

## 五、两处必须在报告里一起写的限定

1. **"应用层"是一个整体名词，不是定位。** 本次只证明了"墙在 Redis 协议之上"，
   没有继续拆到 Spring MVC / Lettuce / 连接池中的哪一层。
   唯一可以指出的线索：`application.yml:44` 的 `max-active: 64`。400 并发对 64 个连接，
   排队系数约 6.25——这个数量级与 60.4ms vs 4.78ms 的差是同一个量级，
   **但它目前只是一个算术上的巧合，不是观测，不能写成结论。** 要坐实得单独做连接池 A/B。
2. **redis-benchmark 是闭环客户端**，400 个连接、发一个等一个，与 B1 的闭环 400 并发同类；
   它不是开环，所以这个数回答的是"Redis 在 64/400 个并发连接下能跑多快"，
   不是"Redis 的绝对上限"。真正的单线程上限由 `usec_per_call=4.64µs` 反推约 21 万/s，
   但那是算出来的，不是测出来的。

## 六、兼容性说明：这条结论对 NFR-6 的地位

Q4 回答"6,617 为什么不能再高"，与 NFR-6 的 8,000 QPS 端到端**不是同一个问题**：
- Q4 的链路是 HTTP → Redis，没有 MQ、没有消费者；
- NFR-6 要的是端到端，含 MQ 发送与落库。

所以即使应用层被证明是墙，**也不能推出"端到端做不到 8k"**——中间还隔着异步链路。
NFR-6 的裁决仍归 Q7。这条边界写在这里，是为了防止后文把两个墙混成一个。

r1 的 `quota:stock:1` 与 MySQL `remain` 一字未动。
