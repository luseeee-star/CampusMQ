# B5 / B6 / B7 · 三段实测（2026-11-09 16:30–17:00）

## B5 · 消费端停机 60 秒

**做法**：`reset?resourceId=1&quota=30000` → 杀掉消费端（`slot-consumer.jar`，PID 189104，8082）
→ 100 并发压 60 秒 → 拉起消费端 → 跟踪 `pending`。

压完立刻读（消费端仍停）：

```
totalQuota 30000  dbRemain 30000  redisRemain 0
records 0  idemKeys 30000  pending 30000  drift −30000  balanced false
```

- **`pending` 峰值 = 30,000 = 成功数**，一份不差。`drift = −30000 = −pending`，是"还没落库"，不是"丢账"。
- `balanced=false` 是**预期形态**（`idemKeys > records`），不是故障。

拉起消费端后：

| 时刻 | records | dbRemain | pending |
|---|---|---|---|
| 0s | 0 | 30,000 | 30,000 |
| 5s | 595 | 29,406 | 29,406 |
| 60s | ~16,000 | — | — |
| 116s | **30,000** | **0** | **0** |

**追平 30,000 条用了 116 秒 ≈ 258 条/s**，曲线单调、没有"恢复瞬间归零"——
后者才是消息被位点跳过的信号，本次没有出现。

> 与 B3 的 102–122 条/s 不矛盾：那一次积压 19 万条、notification 同步在写，
> 同一行 `remain` 的行锁争用更深。**消费速率随积压深度下降**，写报告时要带上积压量。

## B6 · 入口到底碰不碰 DB：数 `Questions`

停着消费端做（否则消费端的 INSERT/UPDATE 会把读数淹掉），1 秒粒度采样 `SHOW GLOBAL STATUS LIKE 'Questions'`。

**空转 30 秒基线：100 次（3.33 次/s）**——sweeper 每 500ms 一轮，每轮不止一条查询。

**压 61 秒（100 并发）**：

```
Questions  2631988 → 2634398 = 2410
扣掉空转基线 61 × 3.33 ≈ 203
入口贡献 ≈ 2207 次 ≈ 37 次/s
```

1 秒粒度（每秒增量）：

```
7  103  10  212  10  7  213  9  9  212  9  8  7  9  8  7  9  7  8  7  9  8
   ▲        ▲       ▲        ▲
```

**结论**

1. 入口平均 DB QPS ≈ **37**。压测本体 **60 秒**（`b6-press.txt` 的 `window 60s per step`）共
   **739,248 个请求**（30,000 成功 + 709,248 个 2001，吞吐 **12,319 req/s**）；
   `Questions` 是 **61 秒**窗口前后对账，多出的 1 秒只贡献约 3 次 SQL，可忽略。
   回源占比 **0.30%**（2,207 / 739,248）。
   所以 B1 的曲线**没有被惊群污染**——量级差三个数量级。
   （原稿这里写的 2,500 req/s / 1.5% 是拿 B4 停机段的吞吐当分母，分子分母不同窗口，已作废。）
2. 单秒采样的脉冲是 **212–213 次**。`loadFromDb` 是 2 条 SQL（`selectById` + `countByResource`），
   按这个数一次脉冲 ≈ **106 个请求同时回源**。**但那一列没有时间戳**：每个点要先起一次
   `docker exec`，实际间隔约 1.4 秒，所以"脉冲间隔 3 个点"推不出真实周期，
   `2,207 ÷ 106 = 20.8` 也对不上 5 秒 TTL。**周期与单脉冲规模以 §P1 的带时间戳复采为准。**
3. 这比按"1–2ms 回源窗口 × QPS"推算的 7–14 **大一个数量级**，机制解释是正反馈：
   一批 SELECT 排在 64 个连接前面，回源窗口被自己拖长到几十毫秒，窗口越长吸进的请求越多。
   **注意这只是解释、不是对照实验**——§P2 用 200 并发做了对照，用来区分"正反馈"与"连接池封顶"。
   **惊群规模不能按单次回源耗时去推，必须实测。**
4. 空转基线的 3.33 次/s 比预估的 2 次/s 高，说明 sweeper 每轮不止一条查询；
   不先量基线，12 和 2,400 分不清。

## B7 · 磁盘写满时 Redis 的表现（旁路 64MB tmpfs）

生产那一套不能打（容器 `/data` 1007G、宿主 C 盘只余 81G，按 95% 计算要写 899GB，
先炸的是 Windows）。改用一次性容器：

```bash
docker run -d --name b7-redis --tmpfs /data:size=64m redis:7-alpine \
  redis-server --port 6379 --dir /data --appendonly yes --appendfsync everysec
docker exec b7-redis redis-benchmark -n 200000 -d 1024 -r 1000000 -t set -q
```

灌到 100% 后：

| 观测 | 结果 |
|---|---|
| 写命令 | `MISCONF Errors writing to the AOF file: No space left on device` |
| `SET` / `INCR` | **都拒**（不是"照收不报"） |
| 读命令 | 正常，`dbsize` 60,814 保留 |
| `aof_last_write_status` | **err** |
| `rdb_last_bgsave_status` | ok（此时没在 bgsave） |
| `df /data` | 64.0M / 100%，余 12K |
| AOF incr 文件 | **67,086,187 字节 = 63.98 MiB**（上限 64 MiB = 67,108,864 字节，**小 22,677 字节**，占 99.97%） |

**两个要点**

1. **拒写，不是静默接收**。所以磁盘满不会让 `quota:stock` 虚高——
   扣减失败 → EVAL 抛错（`RedisScriptRunner:159` 只吞 NOSCRIPT，其它重抛）→ 入口返回 9001。
   风险是**可用性**（全场申领失败），不是**正确性**（超发）。
2. **AOF incr 文件被填到设备容量的 99.97%（67,086,187 / 67,108,864 字节，差 22,677），下一次 write 就失败。**
   原稿写成"67MB > tmpfs 64MB"，是把 `df` 的 `64.0M`（MiB）当十进制 MB 去和 67,086,187 字节比大小：
   64 MiB = 67,108,864 字节，文件比上限**小** 22,677 字节，方向反了。
   （`÷1,048,576` 得 MiB = 63.98，`÷1,000,000` 得 MB = 66.99，两个数不能用同一个单位名。）
   至于"尾巴是否被截断、重启要不要 `aof-load-truncated yes`"，当时没有重启验证——
   后来在旁路容器里补了两次（`b7-aof-restart.md`）：**能起来、无告警、AOF 长度一字未变，
   只丢缓冲区里没落盘的那几条（1 条 / 9 条）**。
   但这一次**没有触发截断**：真触发时必然同时出现「文件变短 + `!!! Truncating ... at offset N !!!`
   + `short read` 警告」，实测三件都没有，说明尾部本来就落在命令边界上。
   于是又构造了一次残缺 AOF 来正面测（`b7-aof-truncation.md`）：默认 `yes` 会截断尾命令后正常启动
   （文件 133→110）、设 `no` 则 `exit 1` 拒绝启动并提示 `redis-check-aof --fix`。
   所以原句**成立**的是「尾部残缺要靠 `aof-load-truncated yes` 才能起、否则得手工修」；
   **作废**的是「本次就是靠它救回来的」——本次尾部完整，加载器根本没进截断分支。

**边界**：单机上无法安全验证"宿主机磁盘满 → MySQL 一起不可用"（vhdx 共用一块盘，
真打满会连 Windows 一起卡死，连删文件的命令都执行不了）。这条按"未验证"写进报告，
而不是按"测过且没事"写。
