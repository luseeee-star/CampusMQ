# P1 · 元信息缓存的真实周期与惊群规模（2026-11-09 17:47）

## 为什么重做

上一轮 B6 的 1 秒采样列没有时间戳（每个点要先起一次 `docker exec`，实际约 1.4 秒一个点），
所以"脉冲间隔 3 个采样点"既可能是 3 秒、也可能是 4.2 秒；`2,207 ÷ 106 = 20.8` 次脉冲
也对不上 5 秒 TTL。**周期和单脉冲规模都不能从那一列读出来。**

这次换成两路独立观测：

- **TTL 锯齿**：在 `cs-redis` 容器内以 5 Hz 采 `PTTL quota:res:1`，重填瞬间 `PTTL` 会跳回 ~5000；
- **总账**：压测前后各读一次 `SHOW GLOBAL STATUS LIKE 'Questions'`，扣掉空转基线后除以脉冲次数。

不需要再按秒采样，脉冲次数由 TTL 锯齿直接给出。

## 配置

```bash
# reset 的 quota 传 0 是无效的（ClaimDevController:148 是 quota>0 ? quota : existing）
curl -X POST "…/api/claim/dev/reset?resourceId=1&quota=1"   # 只留 1 个名额
Stop-Process <slot-consumer 8082>                            # 消费端停掉，避免它的写淹没 Questions
java BaselineHammer … 100 1 1 /api/claim/mq resourceId --sweep=100 --seconds=30
```

`quota=1` 让第一个请求成功后 `stock` 归零，其余请求直接吃 2001——
**不产生消息、不触发消费端落库**，但 `metaCache.get()` 仍在 lua 之前，所以惊群照旧发生。

## 周期：5.000 秒，TTL 假设成立

两次压测各 6 次重填（`PTTL` 从 0~200 跳回 4,850~5,000）：

| 组 | 重填间隔（ms，相邻检测点差） | 均值 | 采样粒度 |
|---|---|---|---|
| A（100 并发） | 4,978 / 5,167 / 4,963 / 4,960 / 4,963 | **5,006** | ±207ms |
| B（200 并发） | 4,989 / 5,177 / 4,964 / 4,971 / 5,172 | **5,055** | ±207ms |

两组都落在 5,000ms ± 采样粒度内，与 `meta-cache-ttl-ms: 5000` 一致。
**上一轮"3 秒周期"是采样节奏造成的假象**，不是缓存行为。

## 单脉冲规模：≈ 在途请求数

| 组 | 并发 | 吞吐 | 平均 RT | 在途（avg/peak） | Questions 增量 | 每次脉冲回源数 |
|---|---|---|---|---|---|---|
| A | 100 | 12,682 | 7ms | 99 / 100 | 1,225（扣基线 107 ≈ 1,118） | 1,118 / 6 ÷ 2 ≈ **93** |
| B | 200 | 13,386 | 14ms | 199 / 200 | 1,997（扣基线 107 ≈ 1,890） | 1,890 / 6 ÷ 2 ≈ **158** |

（÷2 是因为 `loadFromDb` 一次两条 SQL：`selectById` + `countByResource`。）

**判读**：

1. **不是连池封顶。** 若 64 个 Hikari 连接是上限，两档应该卡在同一个数（≤64 个并发回源，
   ≈128 条 SQL/脉冲）；实测 93 → 158，随并发涨了 1.7 倍。
2. **≈ 在途请求数**，也就是 `QPS × RT`：
   - A：`12,682 × 7ms = 89`，实测 93；
   - B：`13,386 × 14ms = 187`，实测 158。
3. 所以**回源窗口 ≈ 一个请求的完整处理时间，而不是那 1–2ms 的 DB 往返**。
   键一过期，接下来一个 RT 内进来的请求全都 miss，这就是"一次脉冲吸走一整批"的来源。
   按 1–2ms 窗口推算的 7–14 之所以差一个数量级，是把窗口取错了。
4. 对 B1 的影响：脉冲规模与并发同阶（百级），相对 2,342–9,256 req/s 的吞吐是**每 5 秒
   一次、每次 ~93 个请求**，折算下来 **0.3% 量级**，不改变 B1 的任何结论。

## 边界

- `quota=1` 时 `stock` 恒 0，走的全是 2001 快速失败路径，**不是成功申领路径**。
  惊群读的是 `metaCache`，与 lua 返回什么无关，所以这个替换不影响规模；
  但"成功路径下的 RT"不能引用本表。
- 两档的吞吐几乎一样（12,682 → 13,386），说明 2001 快速路径本身在 ~13k req/s 饱和，
  加压只把 RT 从 7ms 抬到 14ms（Little's law）。所以 200 并发组**不能**当吞吐对照。
