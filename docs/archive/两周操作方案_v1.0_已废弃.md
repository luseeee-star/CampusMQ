## 2. D0（今天）· 环境与工程准备清单

今天不写业务代码，只把地基打好。验收标准：空的五模块工程能 `mvn clean install` 通过，git 有首次提交。

1. `git init` + 首次提交（现有骨架原样入库，留作历史）。
2. **重构 pom 为聚合父工程**，建五个模块（对应执行方案 §2.1）：
   - `campusmq-common`：协议、编解码、错误码
   - `campusmq-client`：生产者 / 消费者 SDK
   - `campusmq-broker`：Broker 服务端
   - `campusmq-demo`：校园名额发放业务
   - `benchmark`：压测工具与实验脚本
3. 父 pom 统一依赖版本：Netty 4.1.x、JUnit 5、slf4j + logback、Jackson；删除 war packaging 与 junit 3.8.1。
4. 装 MySQL 8（本地单实例即可），建好库 `campus_quota`，**提前开启慢查询日志**（`slow_query_log=1, long_query_time=0.5`）——E1 实验要靠 `Slow_queries` 计数器出数。
5. 写 `LOGBOOK.md` 第一行（格式见执行方案 §8 末尾，今天就可以记：例如"原骨架是 war 包，不符合多模块设计，推倒重建"）。
6. 检查 .gitignore：补充 `store/`（Broker 运行产生的 commitlog 等数据文件）、`*.log`。

## 3. 四阶段执行要点

以下为对执行方案 §8 排期的操作化补充（每日任务、止损线以原文为准，此处只加"怎么算过"）。

### 第一阶段 D1–D5 · 存储引擎

| Day | 过关验证（跑不通不收工） |
|---|---|
| D1 | 命令行启动 Broker + 客户端，发送一条消息收到响应。**EOD 决策点：Netty 若无实质进展，D2 起切 HTTP，不犹豫** |
| D2 | 写满一个 128MB 文件后继续写，**单测验证跨文件滚动读取正确**（风险表最高危项，当天必写这个单测） |
| D3 | 进程重启后能完整读出历史消息；故意写坏尾部半条，验证 magic 校验能识别 |
| D4 | 按 topic 拉取到消息；卡住则退化为"启动时全量重建索引"，先保功能再保性能 |
| D5 | 两个消费组从同一 topic 各自独立消费，offset 文件落盘、重启续费 |

### 第二阶段 D6–D8 · 可靠性与延迟

- D6：写"固定失败消费者"测试桩，亲眼看到退避序列（1s→5s→10s→…）与第 16 次后进死信。
- D7：发一条 30 秒延迟消息，掐表验证到期才可见。
- D8：分层时间轮（3 层）；**超时就降级为单层时间轮 + 优先级队列兜底，精度 1s 可接受**（NFR-5 目标 P99 < 1s）。

### 第三阶段 D9–D11 · 崩溃恢复与业务接入

- D9：三组场景验证——优雅关闭重启 / `kill -9`（Windows 用 `taskkill /F /PID`）后重启 / 写一半强杀。记录恢复耗时（NFR-7 目标 < 10s）。
- D10：建 5 张表（§7.1），抢占接口 + `(resource_id, student_id)` 唯一索引 + `UPDATE ... WHERE remain > 0` 条件扣减。**一致性压力只放数据库，不放中间件**（§7 并发清单最后一行）。
- D11：超时释放走延迟消息（不是定时扫表）；通知 / 学分 / 余量三个消费者至少保一个跑通全链路，其余可减。

### 第四阶段 D12–D14 · 实验与交付（不可砍）

- D12：E1（有/无 MQ 削峰对照）、E2（SYNC / ASYNC_100MS / ASYNC_500MS 三档刷盘，各写 100 万条后 kill -9 数丢失量）。
- D13：E3（5s/60s/1800s 三档延迟精度，共 1000 条）、E4（10 万→100 万条灌入，记录堆积与追平曲线）+ 至少一次故障注入排障记录。
- D14：README 按**实验报告**格式写（不是功能清单）、简历文案四条、高频问答 Q1–Q4 各练一遍。

## 4. 实验纪律（§9.0 落地为操作细则）

1. 每组实验建一个目录：`benchmark/e1/`…`e4/`，内含：脚本、原始输出、图表、结论.md（目的/变量/固定条件/观测方式/原始数据/结论，六段缺一不可）。
2. 每组实验必须有对照组，只给一个数字等于没给。
3. 反例必须记录——尤其 E2，"异步刷盘 500ms 在写入速率 X 时丢 Y 条"这种数据是项目胜负手。
4. E1 报告必须写"威胁到有效性的因素"：压测端、Broker、MySQL 同机互相抢资源，只做相对对比，不做绝对值宣称。

## 5. 每日固定动作

1. 开工前：确认当日"当日产出"是什么（排期表里那一格），不扩散范围。
2. 收工前：往 `LOGBOOK.md` 写一行"今天没按预期发生的事"（没有就写"无"，但 14 天下来至少 10 条是验收项）。
3. 每天 git commit 至少一次，commit message 带 Day 编号（如 `D4: consumequeue reput service`）。

## 6. 风险决策点（到点必须做决定，不拖）

| 时点 | 决策 |
|---|---|
| D1 收工 | Netty 卡住 → 切 HTTP（通信层不是验证核心，存储层才是） |
| D2 收工 | 跨文件读写单测不过 → 当晚修完再走，这是最高危项 |
| D7/D8 超时 | 时间轮降级为单层 + 溢出优先级队列 |
| D11 收工 | 业务没做完 → 砍到只剩抢占 + 释放，D12 照常开始 |
| 任何一天 | 对照 §0 权重表砍功能，永远不动 D12 / D13 |
