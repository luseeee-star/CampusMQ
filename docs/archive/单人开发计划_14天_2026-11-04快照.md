## 0. 开始前必须定死的三件事

### 0.1 范围：砍掉一切不产生数据的部分

| 砍掉 | 替代方案 |
|---|---|
| 前端页面 | 一个最简 HTML + curl 脚本，时间盒 **半天**，D11 做 |
| 管理端界面 | 只做 2 个 HTTP 接口（建活动、导对账），不做页面。G-2 配置资格**并入建活动**，不单独开接口；G-3 发放进度在 D9 单独做 |

| K8s | docker-compose |

不做这些不是偷懒：**它们不产生任何并发数据，占用的是你最缺的时间。**

**执行后（2026-11-04）**：这张表基本照做，两处偏离——
① 通知不只是"写表"，做成了写表 + 退避重试（SYS-2 要求"失败可重试"，只写表不满足）；
② 前端在 D11 直接砍掉（§3 第一砍），管理端接口保留。

### 0.2 环境：时间盒 1 天，超时就降级

| 组件 | 方案 | 降级方案（装不上就用这个） |
|---|---|---|
| Redis 7 | Docker | 本机装 Windows 版 |
| RocketMQ 5.x | Docker（broker + proxy 两个容器） | **降级为 Redis List 做队列**，先跑通链路，D3 再换回来 |
| MySQL 8 | Docker 或本机 | 本机 |
| 压测 | Gatling 独立容器 | JMeter |

**Docker 起 RocketMQ 是最可能卡住的地方。** 卡超过半天就直接降级，不要死磕——队列用什么是次要的，链路跑通才是主要的。

**执行后（2026-11-04）**：RocketMQ 5.x **没有降级**，broker + proxy + dashboard 五容器起来了。
但踩了两个环境坑，都写进了 README：
- D 盘常驻 90%，触发 Broker 的 75/85/90 三道磁盘闸，所有写入被拒成 50001 → store 挪到 C 盘；
  后来 `diskMaxUsedSpaceRatio` 从 88 抬到 95。**所以 D10 的磁盘实验要填到 96% 才会触发拒写。**
- Docker 冷启动时 store 里的 `abort` 文件会触发异常恢复，worker 挂 → 队列满 → main 永久阻塞。
**压测工具没有用 Gatling**，原因见 §4（结论：自研 hammer 反而拿到了 Gatling 拿不到的判据）。

### 0.3 压测机：一台电脑也要做隔离

学生只有一台电脑，压测端和被测端在同一台机器上，数据会有偏差。务实的做法：

```
Docker 限制应用容器 CPU：--cpus=2
Gatling 跑在另一个容器，限制 --cpus=2
这样至少 CPU 是隔离的，RT 数据可用作相对对照
```

**务必在报告里注明"本机压测，数据用于相对对照，非绝对容量"。** 这句话写进 README，面试时主动说出来，比被人问出来强。

**执行后（2026-11-04）**：**没有做 `--cpus` 隔离**。应用直接 `java -jar` 裸跑在 Windows 上，
和压测器共用 32 核。所以报告里"容量"只能讲相对对照，绝对值换机器不成立。
代价要主动说：`1.33ms/fsync` 是 WSL2 + Docker Desktop 的产物，323 条/s 这个绝对值出不了这台机器，
但"减少 fsync 次数带来 3.4x"与平台无关。

### D1 · 裸数据库版：先亲眼看见超卖

不要一上来就上 Redis。**先做一个必定超卖的版本，把它测出来**——这是后面所有设计的对照组，也是简历上最有说服力的一组数据。

```
1. MySQL 建两张表：activity（总名额、余量）、slot_record（学号 + 活动ID 唯一索引）
2. 写一个接口：SELECT 余量 → 判断 > 0 → UPDATE 余量 -1 → INSERT 记录
3. 用 Gatling 打 200 并发，名额设 200
4. 记录：成功数、超卖数、RT
```

**当天验收**：超卖数 > 0，截图保存。这句"裸 DB 版本在 200 并发下超卖 37 件"就是简历上第一句话的由来。

**落地（2026-10-27）**

- 实现：200 并发、共 600 次请求，三轮分别超卖 **86 / 71 / 65 件**，每秒处理 370 次，对照组数据到手。
- 未实现：无。但建不到原计划说的 `activity` / `slot_record` 两张表上——主库给余量加了"不能小于 0"的约束，并发下会直接报错，拿到的是异常而不是超卖数；改成另建两张什么约束都没有的 `bare_*` 表。
- 改动：压测工具从 Gatling 换成一个 Java 文件 `benchmark/hammer/BaselineHammer.java`，直接跑。原因：这天只要数一数成功、失败、超卖各多少，搭容器的成本换不来东西，Gatling 留到 D5。另外压测必须关掉 SQL 日志，否则日志拖慢执行，超卖会从 86 缩到 54–67 件，把问题藏掉一半。
- 改动：判定标准从"三个数互不相等"改成只看"余量有没有变成负数"。原因：记录数本来就等于扣减数，原写法把一对必然相等的数当成了两个独立验证。

### D2 · Redis Lua：让超卖归 0

```lua
-- KEYS[1]=余量key  KEYS[2]=已抢集合  ARGV[1]=学号
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[1]))
if s == nil or s <= 0 then return 0 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

返回值语义定死：**1 抢到 / 0 已满 / -1 已参与**。这个约定后面所有代码都依赖它，不要改。

**当天验收**：同样 200 并发，超卖数 = 0，连跑 5 轮。

**落地（2026-10-27）**

- 实现：200 并发连跑五轮全部正常，**超卖 0**，账面也没有差。脚本落地为 `claim_basic.lua`，返回值多加了一个 **−2 表示"库存数据不存在"**（后面要做删数据的故障实验，得有自己专门的症状，不能和"已经抢完"混在一起）。
- 未实现：无。
- 改动：验收标准从"既看正确性又看速度"改成**只看正确性**。原因：实测每秒 317 次，比 D1 的 385 还**慢了 18%**——换成 Redis 只是把"谁来判定"挪了个位置，写库的两次往返一次没省。速度的提升实际发生在 D3。
- 改动：完整版的 `claim.lua` 推迟到 D4 才启用。原因：如果提前把防重复、学院配额塞进对照组，两组之间的差异就说不清是谁带来的。

### D3 · MQ 异步落库：把落库移出用户等待

```
扣减成功 → 发消息 → 立即返回
消费者：幂等 INSERT（唯一索引兜底）+ 数据库余量 -1（同事务）
```

**当天验收**：入口 RT 从 D1 的多少降到多少（记录在案）。这是"异步化降低 RT"的直接证据。

**落地（2026-10-27）**

- 实现：每秒从 364 提到 **490 次**（涨 35%），一半请求的耗时降了 61%；手动停掉消费者再压 200 次请求，重启后自己追平了。
- 未实现：无。
- 改动：结论改了，从"异步能带来数量级提升"改成**"异步只是把等待挪了个地方"**。原因：发一条消息和写一次库，对请求线程来说是同一种等待。真正的数量级提升来自 D7 去掉的那把锁（2.27 倍）。
- 改动：账对不对的判断，从"记录数等于成功数"改成"等排队数归零"。原因：改成异步之后，压测刚结束那一刻记录必然还差几条，按原标准会误判成丢消息。另外第一轮的数据要丢掉：后三轮是 505–515，第一轮只有 336，差的 50% 是刚启动时各种缓存还没热。

### D4 · 幂等：重复请求返回首次结果

```
requestId → 缓存首次响应（含结果、订单号），TTL 60s
重复请求直接返回这份缓存
```

**当天验收**：同一学号提交 3 次，三次响应体完全一致（不是"你已参与过"）。

**落地（2026-10-27）**

- 实现：同一个学号提交三次，三次返回的内容一字不差；是不是重复请求，靠响应头 `X-Claim-Replay: 1` 告诉调用方。学院配额的分支顺手做完了，默认关着。
- 未实现：无。
- 改动：结果缓存的保存时长从 60 秒改掉，两条链路分别按活动情况算：同步入口 40 分钟，异步入口约 7.9 天（差 47 倍是故意的）。原因：60 秒根本活不过一场跨天的活动，学生过一会儿再点，会被当成一次全新的申领——Redis 里多扣了一个名额，数据库却没有对应记录，这个差额永远平不了。

### D5 · 压测基线：找出拐点（最关键的一天）

阶跃加压：500 → 1000 → 2000 → 4000 → 6000 → 8000 QPS，每档持续 60 秒。记录每档的：

| 记录项 | 用途 |
|---|---|
| 吞吐（实际完成 QPS） | 画饱和曲线 |
| P50 / P99 RT | 画恶化曲线 |
| 失败率 | 找可用性边界 |
| Redis CPU | 判断是否到 Redis 上限 |

**当天验收**：一张表 + 一条结论："单 key 判定在 X 万 QPS 出现拐点，P99 从 A ms 涨到 B ms"。**这张表是整个项目最值钱的东西。**

同时补跑分层对照（D1/D2/D3 三个版本各压一遍），回答"每一层到底挡住了多少"。

**落地（2026-10-28～29，用了 2 天）**

- 实现：**200 并发处出现拐点**，之后再加并发吞吐基本不动（±1%）。同一套系统量出四个数：带锁 6,700、去掉锁的探针 27,800、主链路去掉锁 11,300、端到端 3,850。
- 未实现：无。但原定一天不够——拐点只是一条曲线，三项指标的对账、三层对照、定量投递的验证各要另跑一套。
- 改动：加压方式从"每档固定压力跑 60 秒"改成"逐步加并发 + 定量投递，两种方式互相印证"。原因：跑 60 秒的窗口里，消费端每秒只处得了 323 条，积压会把入口的容量盖住，量到的就不是入口能力了。
- 改动：核心数字从"单 key 的拐点"改成**"曲线形状 + 三个数并列"**。原因：4,007 是**带锁**时量的——400 个请求线程里有 393 个卡在同一把 Java 全局锁上（`getSha1()`），6,700 是这把锁的上限，不是链路的上限。
- 改动：三项指标重新判——七成以上档位达标，**每秒 8000 那一项明确不达标**（端到端只有 3,850）。原因：原表把"计划落点"画成了"已经达标"，这是最容易被一句话问穿的地方。
- 口径：原来说的"压测工具上限 4,500"已经被推翻，同一个接口实际能打到 45,600。报容量必须同时交代三件事：跑多久、客户端热没热、服务端热没热——同一个数在三种状态下分别是 4,188 / 5,541 / 6,746。

### D6 · 网关限流：阈值从 D5 反推

```
阈值 = D5 实测容量 × 0.7 ÷ 实例数
```

用 Sentinel 或 Spring Cloud Gateway 内置限流器都行，重点是**阈值必须有出处**，不能拍脑袋。

**当天验收**：压到容量的 3 倍，放行量稳定在阈值附近，被拒请求 RT < 5ms。

**落地（2026-10-29）**

- 实现：把限额设成 1000 时，实际放行 **1,027 次/秒**（多 2.7%），该放行的场景一次都没误伤；被拒绝的请求，服务端判断只花 **1.86 微秒**。
- 未实现：无。
- 改动：阈值没有按"容量乘 0.7"算，直接定成 **3000**。原因：3000 是最后一个还舒服的档位（99% 的请求 145 毫秒内完成，能处理掉输入的 98%），到 4000 就掉到 76% 并且超过 200 毫秒。百分比那个算法没有依据。
- 改动："被拒请求 5 毫秒内返回"拆成两个数：服务端判断 1.86 微秒；端到端一半 1 毫秒、99% 6 毫秒。原因：6 毫秒是压测工具自己的调度下限（它每轮最多睡 2 毫秒才发下一批），拿它去判断限流器的快慢会得出错误结论。
- 待办：3000 是单 key 时候定的，D7 之后主链路已经到 11,300。**不重新定，"容量一万多"和"线上 3000 就拒"两句话会自相矛盾——D10 之后必须重定。**

### D7 · 库存分片：越过单 key 上限（最难的一天，也是最大亮点）

**当天验收**：再压一遍，对比 D5 —— 吞吐提升多少、P99 降多少。

**必须想清楚并写进 README 的问题**：某个分片卖完、别的还有，怎么处理？答：允许短期不均，靠活动结束后统一结算；分片数越大，不均的绝对值越小。

> 这天做不出来就跳过，直接进 D8。**但要在 README 里写明"单 key 到 X 万 QPS 触及上限，分片方案已设计未实现"**——如实说明比假装做过好。

- 未实现：库存分片。不是没做完，是判定不该做。
- 改动：D7 的主题从"做分片"改成**"判断该不该做分片"**。原因：分片最多只能带来 12% 的提升（它只分摊 Redis 的压力，摊不平连接池单线程已经跑到 89%），而 D8 阶段去掉那把锁之后，主链路已经有 11,300。
- 改动：把"那把 Java 全局锁"提为主要结论。原因：400 个线程里 393 个在等它；对照实验里同一个接口去掉锁之后从 5,669 涨到 **25,357（4.47 倍）**——6,700 是这把锁的上限，不是链路的上限。
- 改动：失败结论也写进报告。原因："量了三条判据，结论是不做"比"硬做了分片"更能说明判断力。

### D8 · 超时释放 + 补位队列

- 用 RocketMQ 延迟消息（或 Redis ZSET 到期扫描）实现 30 分钟释放
- 取消必须 `SREM` 判返回值（漏判会导致余量虚增）
- 释放的名额进补位队列，不重新开放抢号（需求 R-6）

**当天验收**：投放 1000 个不同到期时刻的锁定，释放误差 P99 < 1s；同一学号取消 10 次，余量只回补 1 次。

**落地（2026-11-03～04，用了 2 天）**

- 实现：确认、取消、超时释放三条路的分支全部走通；释放的延迟稳定在 0.5 秒左右，一台机器每秒能放 65 个名额；通知连续失败 7 次后判死，实测 **64.3 秒**；锁定成功的通知 2 秒内送达。
- 未实现：**退掉的名额给排队同学，这条直接违反了需求 R-6**。原因：补位要单独建一个队列再筛一遍人，时间不够，收益也不如 D9、D10。**README 里必须写明，不能只在计划里打个"没做"。**
- 未实现：原计划的"定个闹钟到点释放"。原因：这个闹钟在代码里只有一个名字，没有任何地方真的发出去过，能用它的只有开发用的手动测试接口；现在唯一的释放方式是每半秒扫一遍数据库，一次拿 100 条，每条单独一个事务。
- 改动：取消没有按原计划"从名单上划掉名字、看划没划掉"，改成先改数据库记录——只有还处于"锁定中"的那一条才能改成功，改成功之后再回补 Redis。原因：顺序反过来，一旦数据库那步失败，名额就凭空多出来，而且没有第二次机会扣回去。**取消时也绝不删 Redis 里那条防重复的记录**，删了学生再点一次就会重新扣、重新发消息，消费端撞上唯一索引不认，于是名额少发。
- 改动：通知重试从"3 次、每次隔 5 秒"改成**从 1 秒起翻倍，最多 7 次**（1 / 2 / 4 / 8 / 16 / 32，共 63 秒），配置、代码默认值、文档四处一起改。原因：既然要求"失败可以重试"，就该一路退到小时级，而不是 15 秒就放弃。
- 改动：释放延迟改成两个数：正常情况下 0.5 秒，积压时 1.3 秒是结构上的下限；同时把 `quota_record` 的 6 个时间字段精确到毫秒。原因：只精确到秒的话，这个延迟根本没法验证。1.3 秒 = 每条 800 毫秒的预算 + 半秒的扫描间隔，换实现也一样。
- 口径：`/api/claim` 这个入口是同步写库、**不发消息**的，拿它去验通知只会得出"链路不通"的错误结论，必须用 `/api/claim/mq`。另外统计覆盖率时分母要带一个时间起点，否则会算出一个假的红灯。

### D9 · 对账巡检

```
每 5 分钟：
  Redis 已抢集合大小  vs  数据库有效记录数
  初始名额 = 剩余 + 已确认 + 已锁定
差异 → 告警 + 记录到 diff 表
```

**当天验收**：手动删掉数据库里 3 条记录，5 分钟内对账任务能报出"差异 3 条"。**对账是消息丢失和消费失败唯一的发现渠道，不能省。**

**开工前（2026-11-04，未开始）**

- 实现：报表的统计口径已经写好并验证过（`deploy/sql/report.sql`），里面写死了一个统计起点 `SET @t0='2026-11-04 17:27:00'`；实测三类事件的通知覆盖率都是满的：锁定 6/6、确认 3/3、超时释放 4/4。
- 未实现：定时任务本身还没写；取消这一列在报表口径下是 **0 条样本**。活动 3 的 17 条释放是 **14 条超时 + 3 条取消**（S5C1 / S5D1 / S5E1，发生在 15:49–15:51），那 3 条早于统计起点 `@t0`，所以没进分母。要让这一列有数，得在起点之后再真的取消一次。
- 五条必须注意：
  - **统计要带时间起点**，不带会算出 19% 的假红灯。
  - **报表本来就只查 r3，不需要写任何"排除活动 1"的条件**。`deploy/sql/report.sql` 四个分支（锁定/确认/取消/超时）全是 `WHERE r.resource_id = 3`，库存平衡那一段也是 `r.id = 3`；只有"通知状态分布"和"未修差异"两段是全量视角，那是它们该有的样子。
    活动 1 仍然不能当样本（被 reset 删过 15.2 万条、历史链断了；剩下 8 条是 S-4 验收样本，16:59–17:09，早于起点自己就不入选），但**它可以当压测靶子**——100 万名额打不穿，正好给 B 块用。
  - **系统自动关账那批要排除**：当前库里释放原因只有 `TIMEOUT` 和 `CANCEL`，一条 `SYSTEM` 都没有。但规则不能删——那个标记是关账脚本一次性写上去的，代码里没有任何地方会生成它；以后再执行关账，还得重新加这个过滤。
  - 记录表里没有"来源"字段，所以覆盖率只对走消息的那个入口成立。
  - **巡检和压测互斥，压测期间必须关掉**。它每 5 分钟扫全表、写 `reconcile_diff`，还会抢数据库连接：B 块注入"删记录"时会立刻告警，把故障信号搅浑。开关用 `campusslot.reconcile.enabled`，和 `ExpiredReleaseSweeper` 的 `campusslot.release.sweep-enabled` 同一个写法。**11-09 上午验完就关，B 块结束再打开。**
- **取数口径：数据库那边必须用 `total_quota − COUNT(status IN ('LOCKED','CONFIRMED'))` 算，不能用 `quota_resource.remain` 这一列。**
  原因很具体：验收动作是"删掉 3 条记录"，而删记录**不会动 `remain` 这一列**。拿它去比，差异恒为 0，
  删 10 条也一条都报不出来，最后看起来像"巡检根本没跑"。对账包说明里写的口径就是这个 count 公式，别自己换。
- **两个方向都要落表**（`source='SCAN'`），只是告警级别不同：正差异（Redis 比库多）立刻按警告处理；
  负差异（Redis 比库少）先按信息记下，**连续 2 个巡检周期仍为负再升级成警告**——在途消息最多只该持续一个周期，
  持续为负就说明有记录真的丢了。如果实现成"只为正差异落表"，当天验收（删记录）必然得到 0 行。
- 两边的差异方向含义相反：Redis 比数据库**少**，是消息还没落库，下次自己就平了；Redis 比数据库**多**，才是真问题——要么有人手动改过，要么回补执行了两次。
- **巡检记录是按活动聚合的**，`student_id` 和 `record_id` 留空（表注释就是这么定的）。所以验收只能验"差 3 条"，
  验不出"差的是哪 3 条"，写验收标准时别加这个要求，否则做到一半才发现做不到。

### D10 · 故障注入：做出故障矩阵（第二关键的一天）

对每个故障，记录三件事：**用户看到什么 / 损失多大 / 多久恢复**。

| 故障 | 注入方式 | 要观察的 |
|---|---|---|
| Redis 主节点挂掉 | docker stop | 是否全链路不可用、扣减记录丢多少 |
| MQ 不可用 | **先 `mqshutdown broker` 让它自己退出，不要直接 `docker stop`** | 已返回"抢到"但没落库的有多少；恢复时间拆成「能接请求」和「索引重建结束」两个数 |
| 消费者卡死 | 消费线程 sleep 60s | 堆积多久追平 |
| 数据库慢查询 | 加一条无索引 SQL | 入口 RT 是否被拖慢（应该不会） |

**当天验收**：一张 4 行的表。**这张表是简历上唯一抄不来的内容**——它只能来自真的跑过。

**开工前（2026-11-04，未开始）**

- **是 5 行不是 4 行**：需求书点名的「**磁盘写满**」要补回来——把容器盘填到 96%，看先出问题的是 Redis 的写入日志还是数据库的日志文件。做不出来就在报告里写"未验证"，不要拿别的凑数。
  **这一行必须排在矩阵最后一行**：它恢复成本最高——Redis 写日志可能被截断、数据库要做崩溃恢复，和"停一下 broker"完全不是一个量级。恢复后**先验账平**（`remain` = 初始 − 已确认，`reconcile_diff` 没有新增）再往下走，否则后面所有数字都建在一个坏掉的环境上。
- **停 broker 必须让它干净退出，否则"多久恢复"这一列测的是自己**。2026-11-05 那次 `docker stop` 强杀，
  重启时 broker 同步重建消费队列索引（`store.log` 里逐条刷 "Maybe try to build consume queue"，
  日志涨到 119MB，速率只有 0.8MB/s，追了 132MB），整个恢复过程 **10 分钟**，proxy 反复重启 10 次。
  这个数字记进报告会被读成"RocketMQ 恢复慢"，实际是环境没干净退出。
  所以：停之前 `docker exec cs-broker sh /home/rocketmq/rocketmq-5.3.0/bin/mqshutdown broker`，等它自己退；
  记录时**拆成两个数**——「服务可用耗时」（proxy 能接请求）和「索引重建耗时」（`store.log` 停止刷那行重复日志）。
  报告里只引前者，后者单独注明是重启方式带来的。
- **压测靶子用 r1，不用 r3**。r3 只有 3000 名额，打穿之后 D9 的报表分母就没了；r1 是 100 万名额，压不爆。r1 被 reset 过这件事不影响它当靶子——报表本来就只查 r3。r1 的 `close_at` 是 **2026-11-11 16:31**，覆盖 11-09~11-10，不用改。
- **每一档压多久要按"消费能力"反推，不要拍 10 分钟。** 此前实测消费侧约 323 条/s：10 分钟 × 3,850/s ≈ 230 万条消息，排空要 2 小时；而 `reset` 在消息没落完时默认拒绝（得传 `force`）。
  所以每档压 **60～90 秒**（约 20～35 万条，排空 10～18 分钟），够画出曲线，也不至于把一整天耗在等队列上。
- **盯 Redis 内存，这是唯一的硬墙。** `maxmemory` 是 1G 且策略为 `noeviction`——撑满时写入**直接报错**，
  症状会伪装成"我正在注入的那个故障"。每次抢号成功都写一个幂等键、TTL 按活动剩余时长算（测试期内不会过期），
  230 万条约 200MB 以上。**每档压前 `reset r1`**（它会清幂等键），并随手记 `INFO memory` 的 used_memory 曲线。
- **r1 这批压测数据怎么处理，现在就要定**：压完 `quota_record` 和 `notification` 各涨几十万到几百万行，
  报表里"通知状态分布"和"未修差异"两段是全量视角，C 块跑报告会明显变慢。
  **建议不删数据，给这两段加时间窗**（`WHERE detected_at >= @b0` / `created_at >= @b0`）——
  数据本身就是证据，删了等于把 B 块的原始记录也扔了。
- **开压之前先把巡检关掉**（`campusslot.reconcile.enabled=false`）。它每 5 分钟扫全表，注入"删记录"时会立刻写 `reconcile_diff`，故障信号和巡检告警会混在一起，分不清到底是谁先发现的。
- **"Redis 出故障"不能只写成"删一个 key"，要按删的是哪类数据分三行**：

  | 删掉的数据 | 症状 |
  |---|---|
  | `quota:stock:*` | 立刻报 `STOCK_CACHE_MISSING(9005)` |
  | `quota:meta:*` | **完全没症状**——代码会自己去数据库再读一遍，只是多一次查询 |
  | `quota:roster:*` | 才会报 `NOT_ELIGIBLE(1005)`；是 1005 不是 1004（1004 是"活动未开始"） |

  只删第三类去验"删 Redis 不影响主链路"，会得到一个假的结论。要造 1005 这个场景得复用测试环境 r2
  （那里有 4 行学院配额，`quota_roster` 里 **200 行名单已经在了**，只需改活动结束时间、把名单灌进 Redis
  ——用 dev 的重置接口就行，**不用等 D11 的建活动接口**）。
- 五条操作纪律（D8 收尾时踩出来的，D10 会反复用到）：
  1. **改消费组配置前先存一份完整记录**——那个命令是整体覆盖的，没写到的字段会被清掉（广播开关就被从"开"改成了"关"）。流程：存档 → 改 → 再取一次 → 逐项对比。
  2. **落库这条链路不许改成"从最后开始读"**——它的意思是不管积压、直接跳到最新位置，等于静默丢掉积压的消息。改成"从头读"最多是重复写一遍，唯一索引挡得住。要干净的起点就另建一个测试用主题，不要动正式的。
  3. **启动服务时日志必须落到文件**——脚本起的进程会被系统回收（两个服务都打印了启动成功然后消失，错误日志是空的）。用工具托管，把输出重定向进文件。
  4. **停服务要按端口找进程**，不能只看记录进程号的那个文件，它经常是过期的。
  5. **插入时忽略重复的写法有个坑**——用 shell 传一段 JSON 进去，引号会被吃掉，结果记成了另一种失败，差点当成"重复被正确丢弃"。改用环境变量传。这两种结果完全不是一回事。

- **A1 补的六条校验，原计划没写**（每一条都对应一种"配了等于没配"或"直接 500"）：
  - `deptId` 必须存在且 `status=1`——`dept_id` 没有外键，传 99 也能插进去；
  - 学院配额非空但 `rosterRequired` 不为 true → 拒绝。学院编码只能从名单取，没名单这层永远不生效；
  - `roster` 非空但 `rosterRequired` 不为 true → 拒绝。名单不会被检查，等于白配；
  - 学院配额合计 ≤ 总名额——超了不是"技术上跑不通"（总余量会先挡），而是页面会承诺一个发不出来的数；
  - `cancelDeadline` 必须落在 `[openAt, closeAt]`——早于开放无意义，晚于关闭等于没有截止；
  - **字段校验失败必须回 1001**。Spring 抛的 `MethodArgumentNotValidException` 原来会落进兜底分支变成
    500「系统繁忙」，调用方会重试而重试永远不成功；时间写成空格分隔也同一个下场。两个异常都补了处理。
- **三类 key 的写入抽成了 `QuotaRedisSeeder`**，没按原计划"给 `ClaimDevController.seedRosterEntries()` 加参数"：
  dev 端点在不带 `dev-endpoints=true` 时根本不装配，发布逻辑不能依赖一个可能不存在的 Bean。
  顺带把 dev reset 也改成调它，覆盖写语义不变（`/reset` 仍是"全清再灌"）。
- **一个新发现的边界，原计划没覆盖**：PUBLISHED 只补缺、且库存 key 缺失时，回填值取数据库的 `remain`。
  如果此刻还有消息没落库，`remain` 比真实余量**大**，补进去等于把在途的又放一遍——
  A1 验收时手工删 key 就撞出了 `pending = -2 / drift = +2`。现在照填（不填是全场 -3，更糟），
  但打一条 P0 error 并在返回 `notes` 里写明"先 drain 再看 drift"。**D9 上线后这类差异应该能被巡检捞到，A3 验收拿它当样本。**
- 改动：**`rosterRequired=1` 时，名单每一行的 `collegeCode` 是必填项，不是可选项。** 拆完判据之后这条才暴露出来：名单成员判定靠的是「从 `quota:roster:{rid}:{sid}` 取到学院编码」，而 `seedRosterEntries()` 灌入时会跳过 `college_code` 为空的行——`quota_roster.college_code` 是 `DEFAULT NULL`，一个只给学号的名单灌完**一个 key 都没有**，发布照样成功，抢的时候全场 1005。所以 DTO 里要强制：`rosterRequired=1` 时每行必须带学院编码，缺了直接参数错误；不要求配 `quota_college` 行，但名单本身必须带编码。
- 改动：活动从"草稿"发布成"进行中"时，必须把三类东西写进 Redis——余量、每个学院各自的那份、以及**名单**。原因：漏掉学院配额的表现是"所有学院的人都提示系统繁忙"，这是故意的——配置不全时宁可拒绝，也不能放人进来。名单同理且更隐蔽：`roster_required=true` 但名单是空的，结果是全场 1005、活动等于自杀。
- **名单写入（G-2）的六条具体做法**：
  - **不进建活动那个事务**。`quota_resource` + `quota_college` 一个事务；名单几千上万行，塞进同一事务持锁太久、撤销日志太大。按每 1000 行一批独立提交，用 `INSERT ... ON DUPLICATE KEY UPDATE`（唯一键 `uk_roster_resource_student` 已经存在），重复导入不会炸。草稿状态下抢不了，分批写是安全的。
  - **发布前校验条数**：`roster_required=1` 而 `SELECT COUNT(*) FROM quota_roster WHERE resource_id=?` 为 0 → **拒绝发布**。这条专挡「名单写到一半就被发布」，那种情况的表现是全场 1005，而且不报错。
  - **名单 key 不设过期**。`seedRosterEntries()` 现在是裸 `set()`、没有 TTL，这是对的，别加：名单过期是**静默失效**（取不到 → 全场 1005），比多占几 MB 内存贵得多。要清就在活动关闭/下线时显式清一次，不进主链路。**反过来，改了活动结束时间就必须重灌名单**——这条进操作纪律。
  - **事后补学院配额，必须把学院 key 一起灌。** 拆分之后多了一条以前不存在的路径：活动建的时候只配名单、不配学院行（`quota_college` 空表），后来想加学院配额，用 SQL 插了几行。缓存最长 5 秒后自动刷新，`needCollegeQuota()` 由 false 变 true，下一笔请求就开始扣 `quota:college:*`——**而那个 key 从来没被灌过**，`DECR` 出来 -1 被判 `-3`「系统繁忙」，全场抢不了。
    以前没人这么建，是因为名单判定被绑在「有没有学院行」上，不配学院行等于名单也不查，那条路走不通；现在两条判据拆开了，路是通的，纪律得跟着补：**插完 `quota_college` 立刻重灌 `quota:college:{rid}:{code}`（值取该行 `remain`），并 `ResourceMetaCache.evict(id)` 让新配置马上生效**，否则会有一段「看着配好了、其实谁都抢不到」的窗口。
  - **入库前校验每行 `collegeCode` 非空**（理由见上面那条改动）：`seedRosterEntries()` 会静默跳过空值，灌完 0 个 key 也不报错。
  - **灌 key 那段不要复制一份**：原来在 `ClaimDevController` 里的 `set()` 逻辑已经抽成 `QuotaRedisSeeder`，
    带 `boolean onlyIfAbsent` 参数——发布 DRAFT 走覆盖、PUBLISHED 走只补缺、dev reset 走覆盖（语义和以前一致）。
    抽出来而不是"给 controller 加参数"的原因：那个 controller 只在 `dev-endpoints=true` 时装配。
- 余量和每个学院配额那两类 key 也**不设过期**：key 缺失等于系统繁忙，不能让它们自己消失。一个 key 几十字节，几万个活动也就几 MB。
- **"可重入"和"可以重复覆盖"是两件事，混在一起写会直接超发。** 顺序固定：**先灌 Redis，最后才迁移状态**（`UPDATE quota_resource SET status='PUBLISHED' WHERE id=? AND status='DRAFT'`，影响 0 行也无所谓）。这样中途失败重跑时一定还停在 DRAFT，能走覆盖写那条分支。写法按状态分流：

  | 当前状态 | Redis 怎么写 | 为什么 |
  |---|---|---|
  | `DRAFT` | **覆盖写**，值取数据库的 `remain` | 没上线、无并发，覆盖正是为了校正上一次的残留 |
  | `PUBLISHED` | **只补缺**（`SETNX`） | 有人在抢，绝不能覆盖已有值 |

  两条都幂等：DRAFT 重复调结果都是 `remain`，PUBLISHED 重复调一个都不写。写成「一律 `SETNX`」会留一个洞——上一次灌了 3000、进程在改状态之前崩了，活动还是 DRAFT；运营把名额改成 2000（`remain` 一起改，否则 CHECK 挡住），再发布时 SETNX 发现 key 存在、一个都不动，状态迁移成功，**凭空多出 1000 个名额**。
- **灌 stock 一律用数据库的 `remain`，不是 `total_quota`。** DRAFT 状态下两者相等（建活动时就是这么插的），PUBLISHED 状态下 `remain` 才是真实余量；用 `total_quota` 回填等于把已经发出去的又加回去，这是超发。`reset()` 里写的是 `total`，因为它在同一个事务里把 `remain` 也重置了——发布的场景不一样，别照抄。`ck_resource_remain_le_total` 这个 CHECK 顺带保证没人能只改 `total` 不改 `remain`。
- **不要写"影响 0 行就直接返回成功、不碰 Redis"那条分支**——如果灌 Redis 失败发生在状态提交之后，`status` 已经是 `PUBLISHED`，再调发布必然 0 行，缺的 key 永远没人补。`EXISTS` 只用来在返回体里告诉调用方"这次补了哪几类"，不参与决策。
- **发布完必须清一次元信息缓存**（`ResourceMetaCache.evict(id)`）。它缓存了活动状态和开放时间，最长 5 秒才自然过期；不清的话"发布后立刻抢"可能被判成"活动还没开放"，演示时看起来像发布没生效。
- **验证可重入别用"连调两次看余量翻不翻倍"**：发布是覆盖写，余量天然不会翻倍，这条几乎必过、什么都证明不了。真判据是**注入失败**——先让灌 Redis 那一步抛异常（临时改错 Redis 地址最省事），发布返回失败；恢复后重跑一次，要求三类 key 齐全且值正确（余量、各学院配额、名单条数）。再补一条：发布成功后**立刻**抢一次，不能出现"活动还没开放"。
- **导对账要提前定「没有学院」这一桶怎么显示。** `quota_record` 里**没有 `college_code` 这一列**，只有 `dept_id`（部门，不是学院）。要按学院分组只能 `LEFT JOIN quota_roster` 拿编码，而这个 join 天然对不齐：
  `roster_required=0` 的活动（r1、r3）一行名单都没有，join 出来整列是空；纯名单活动现在每行都带编码（上面那条改动强制了），但名单外被手工插进来的记录仍然 join 不上。
  所以空桶**必然出现**，不是异常，也不需要"修"。
  两种做法都行：分组列显式保留空值并标注「未分学院」，或者导出参数里给一个「按学院 / 不分学院」的开关。**唯一不能做的是让 `GROUP BY` 把空值那组悄悄丢掉**，那样各学院加起来会对不上总名额。
  顺带一个结论：**学院维度是"名单上写的"，不是"发的时候扣的"**——记录表压根没存这个信息。要在报告里按学院报数，得先说明它来自名单 join，别让人以为记的是扣减那一刻的学院。
- 时间预估：两个接口本体不重，名单这块 **2–4 小时**。当天吃满就别硬做，按 §3 的降级出口走（只建不限资格的活动）。

**建活动接口的必填项现在就要定，否则 DTO 写不下去**

`quota_resource` 里 `dept_id`、`title`、`open_at`、`close_at` 四列都是 NOT NULL 且**没有默认值**（`confirm_timeout_sec` 默认 1800、`roster_required` 默认 0，这两个可以不传）。

其中 `dept_id` 是坑：`dept` 表只有 2 行（XSC 学生工作处、TYB 体育部），而 `quota_college` 里用的 CS / EE / ME / ART 是**学院编码，跟 `dept` 不是一回事**。

- **定成必填，不给默认值。** 库里已经有两种来源的数据（r1、r3 是 XSC，r2 是 TYB），默认值会让接口建的活动全落一个部门；而 `resource` 包的说明写着「所有查询必须带 dept_id 维度」——只有一个取值的维度不叫维度。
- **必须做存在性校验**：`quota_resource.dept_id` 只有普通索引、**没有外键**，传 99 也能插进去变成脏数据。所以先 `selectById` 判存在且 `status=1`，不满足返回参数错误。
- **不做权限校验。** 现在没有管理端身份体系（`StudentContext` 只有学号），写"只能建本部门的活动"只是装饰，伪造成本为零。代码注释里明写「鉴权未做，只校验部门存在」——把边界写出来，比假装做了强。

## 5. 每天的最低纪律

1. **每天必须有 commit**，当天跑不通的代码也要提交到分支，不要留在本地
2. **每组实验必须有对照组**，不允许只记录优化后的数据
3. **失败数据不许删**。并发加到某个值后吞吐反而下降，这是最重要的发现，要写进报告而不是抹掉
