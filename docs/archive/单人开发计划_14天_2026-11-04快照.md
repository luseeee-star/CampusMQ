## 0. 开始前必须定死的三件事

### 0.1 范围：砍掉一切不产生数据的部分

| 砍掉 | 替代方案 |
|---|---|
| 前端页面 | 一个最简 HTML + curl 脚本，时间盒 **半天**，D11 做 |
| 管理端界面 | 只做 2 个 HTTP 接口（建活动、导对账），不做页面 |
| 登录 / 鉴权 | 学号从请求参数传入，不接统一身份认证 |
| 真实通知 | 打日志 + 写通知表，不接短信 / 企微 |
| 微服务拆分 | 单体，部署 2 个实例即可 |
| K8s | docker-compose |

不做这些不是偷懒：**它们不产生任何并发数据，占用的是你最缺的时间。**

**执行后（2026-11-04）**：这张表基本照做，两处偏离——
① 通知不只是"写表"，做成了写表 + 退避重试（SYS-2 要求"失败可重试"，只写表不满足）；
② 前端在 D11 直接砍掉（§3 第一砍），管理端接口保留。

### 0.2 环境：时间盒 1 天，超时就降级

| 组件 | 方案 | 降级方案（装不上就用这个） |
|---|---|---|
| Redis 7 | Docker | 本机装 Windows 版 |
| RocketMQ 5.x | Docker（broker + proxy 两个容器） | **降级为 Redis List 做队列**，先跑通链路，D3 再换回来 |
| MySQL 8 | Docker 或本机 | 本机 |
| 压测 | Gatling 独立容器 | JMeter |

**Docker 起 RocketMQ 是最可能卡住的地方。** 卡超过半天就直接降级，不要死磕——队列用什么是次要的，链路跑通才是主要的。

**执行后（2026-11-04）**：RocketMQ 5.x **没有降级**，broker + proxy + dashboard 五容器起来了。
但踩了两个环境坑，都写进了 README：
- D 盘常驻 90%，触发 Broker 的 75/85/90 三道磁盘闸，所有写入被拒成 50001 → store 挪到 C 盘；
  后来 `diskMaxUsedSpaceRatio` 从 88 抬到 95。**所以 D10 的磁盘实验要填到 96% 才会触发拒写。**
- Docker 冷启动时 store 里的 `abort` 文件会触发异常恢复，worker 挂 → 队列满 → main 永久阻塞。
**压测工具没有用 Gatling**，原因见 §4（结论：自研 hammer 反而拿到了 Gatling 拿不到的判据）。

### 0.3 压测机：一台电脑也要做隔离

学生只有一台电脑，压测端和被测端在同一台机器上，数据会有偏差。务实的做法：

```
Docker 限制应用容器 CPU：--cpus=2
Gatling 跑在另一个容器，限制 --cpus=2
这样至少 CPU 是隔离的，RT 数据可用作相对对照
```

**务必在报告里注明"本机压测，数据用于相对对照，非绝对容量"。** 这句话写进 README，面试时主动说出来，比被人问出来强。

**执行后（2026-11-04）**：**没有做 `--cpus` 隔离**。应用直接 `java -jar` 裸跑在 Windows 上，
和压测器共用 32 核。所以报告里"容量"只能讲相对对照，绝对值换机器不成立。
代价要主动说：`1.33ms/fsync` 是 WSL2 + Docker Desktop 的产物，323 条/s 这个绝对值出不了这台机器，
但"减少 fsync 次数带来 3.4x"与平台无关。

## 2. 逐日明细

每节保留原计划的"怎么做"。已开工的节末尾追加 **落地**，未开工的追加 **开工前**——
两者都只写三件事：**实现了什么 / 哪点没实现 / 为什么改原方案**。
实测数据、踩坑过程留在 `LOGBOOK.md`，这里不复述。

### D1 · 裸数据库版：先亲眼看见超卖

不要一上来就上 Redis。**先做一个必定超卖的版本，把它测出来**——这是后面所有设计的对照组，也是简历上最有说服力的一组数据。

```
1. MySQL 建两张表：activity（总名额、余量）、slot_record（学号 + 活动ID 唯一索引）
2. 写一个接口：SELECT 余量 → 判断 > 0 → UPDATE 余量 -1 → INSERT 记录
3. 用 Gatling 打 200 并发，名额设 200
4. 记录：成功数、超卖数、RT
```

**当天验收**：超卖数 > 0，截图保存。这句"裸 DB 版本在 200 并发下超卖 37 件"就是简历上第一句话的由来。

**落地（2026-10-27）**

- 实现：200 并发 600 请求，3 轮超卖 **86 / 71 / 65 件**，吞吐 370 req/s，对照组基线成立。
- 未实现：无。但"建在 `activity` / `slot_record` 上"不可行——主 schema 有 `CHECK (remain >= 0)`，并发下先抛 CHECK violation，拿到的是异常不是超卖件数；改独立 `bare_*` 两表（无 CHECK、无唯一索引）。
- 改动：压测器 Gatling → `benchmark/hammer/BaselineHammer.java`（JDK 21 单文件）。原因：D1 只需数成功 / 失败 / 超卖，容器编排成本换不来东西，Gatling 留到 D5。压测必须加 `bench` profile——SQL 日志在持连接期打印，超卖会从 86 掉到 54–67 件。
- 改动：判据从"三个数互不相等"→ 只看 `remain < 0`。原因：`records == consumed` 恒等，原写法把必然相等的一对当成了独立校验。

### D2 · Redis Lua：让超卖归 0

```lua
-- KEYS[1]=余量key  KEYS[2]=已抢集合  ARGV[1]=学号
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[1]))
if s == nil or s <= 0 then return 0 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

返回值语义定死：**1 抢到 / 0 已满 / -1 已参与**。这个约定后面所有代码都依赖它，不要改。

**当天验收**：同样 200 并发，超卖数 = 0，连跑 5 轮。

**落地（2026-10-27）**

- 实现：200 并发 × 5 轮全成功、超卖 **0**、drift 0。落地 `claim_basic.lua`，返回码加 **−2 = 库存 key 缺失**（删 key 的实验要有独立症状，不能和"已满"混）。
- 未实现：无。
- 改动：验收口径从"正确性 + 吞吐"→ **只验正确性**。原因：317 req/s 比 D1 的 385 **慢 18%**，Redis 只换"谁来判定"，`INSERT + UPDATE` 的 DB 往返一次没少；吞吐跃升归 D3。
- 改动：最终版 `claim.lua` 推迟到 D4 启用。原因：把幂等 / 配额提前塞进对照组，两组差异会被混在一起。

### D3 · MQ 异步落库：把落库移出用户等待

```
扣减成功 → 发消息 → 立即返回
消费者：幂等 INSERT（唯一索引兜底）+ 数据库余量 -1（同事务）
```

**当天验收**：入口 RT 从 D1 的多少降到多少（记录在案）。这是"异步化降低 RT"的直接证据。

**落地（2026-10-27）**

- 实现：364 → **490 req/s**（+35%）、p50 −61%；`kill` 消费者后压 200 请求，重启自动追平。
- 未实现：无。
- 改动：结论从"异步带来数量级提升"→ **"异步只换往返"**。原因：同步发一条 MQ 与同步写两次库，对请求线程是同一种等待；数量级来自 D7 摘锁（×2.27）。
- 改动：账平判据从 `records == 成功数` → 等 `pending` 归 0。原因：异步后压测结束那一刻 `records` 必然偏少，原判据会误报丢消息。首轮数据也要丢（336 vs 后三轮 505–515，差 50% 是 JIT / 连接池冷启动）。

### D4 · 幂等：重复请求返回首次结果

需求 R-3 的要求，也是最容易写错的一条。**不要只做"拦截重复"，要做"返回首次结果"**：

```
requestId → 缓存首次响应（含结果、订单号），TTL 60s
重复请求直接返回这份缓存
```

**当天验收**：同一学号提交 3 次，三次响应体完全一致（不是"你已参与过"）。

**落地（2026-10-27）**

- 实现：同学号提交 3 次，响应体逐字节一致；重放标记走响应头 `X-Claim-Replay: 1`。学院配额分支顺手做完，默认关。
- 未实现：无。
- 改动：TTL 60s → 两条链路分开，同步 `confirm_timeout+600`（2,400s）、异步 `max(…, close_at−now+1天)`（≈7.9 天）。原因：60s 活不过一场跨天活动，重复点击会变成一次全新申领——多扣 Redis 却没有记录，`pending` 永久为正。两条链路差 47 倍是故意的。

### D5 · 压测基线：找出拐点（最关键的一天）

阶跃加压：500 → 1000 → 2000 → 4000 → 6000 → 8000 QPS，每档持续 60 秒。记录每档的：

| 记录项 | 用途 |
|---|---|
| 吞吐（实际完成 QPS） | 画饱和曲线 |
| P50 / P99 RT | 画恶化曲线 |
| 失败率 | 找可用性边界 |
| Redis CPU | 判断是否到 Redis 上限 |

**当天验收**：一张表 + 一条结论："单 key 判定在 X 万 QPS 出现拐点，P99 从 A ms 涨到 B ms"。**这张表是整个项目最值钱的东西。**

同时补跑分层对照（D1/D2/D3 三个版本各压一遍），回答"每一层到底挡住了多少"。

**落地（2026-10-28～29，用了 2 天）**

- 实现：拐点 **200 并发**（之后吞吐平坦 ±1%）；四个口径并列——带锁 6.7k / 探针摘锁 **27.8k** / 主链路摘锁 **11.3k** / 端到端 **3.85k**。
- 未实现：无。但原定"一天"不够——拐点只是一条曲线，NFR-1/2/6 对账、分层对照、开环验证各要一套压测。
- 改动：加压方式从"固定 QPS 每档 60s"→ `--sweep` 闭合环 + `--qps` 开环互证。原因：60s 窗口会被消费侧 323 条/s 拖成积压，测出来的不是入口容量。
- 改动：核心数字①从"单 key 拐点 QPS"→ **"形状 + 三口径并列"**。原因：4,007 是**带锁**的数——400 个 Tomcat 线程有 393 个卡在 `getSha1()` 的 JVM 全局锁上，6.7k 是这把锁的容量。

- 口径：原"压测器上限 4500"已被推翻（sweep 后同端点 45.6k）。报容量必须同时说窗口长度 / 客户端是否预热 / 服务端是否预热——同一个数在三种状态下是 4,188 / 5,541 / 6,746。

### D6 · 网关限流：阈值从 D5 反推

```

```

用 Sentinel 或 Spring Cloud Gateway 内置限流器都行，重点是**阈值必须有出处**，不能拍脑袋。

**当天验收**：压到容量的 3 倍，放行量稳定在阈值附近，被拒请求 RT < 5ms。

**落地（2026-10-29）**

- 实现：限额 1000 时放行 **1,027/s**（+2.7%）、不误伤段服务端拒绝 0；拒绝判定 **1.86μs**；无锁 CAS 令牌桶（令牌用 double）。
- 未实现：无。
- 改动：阈值从"容量 × 0.7"→ 固定 **3000**。原因：取的是最后一个 P99 还舒服的档位（3000 档 145ms、处理能力仍占输入 98%），4000 档掉到 76% 并越过 200ms；百分比法没有出处。

### D10 · 故障注入：做出故障矩阵（第二关键的一天）

对每个故障，记录三件事：**用户看到什么 / 损失多大 / 多久恢复**。

| 故障 | 注入方式 | 要观察的 |
|---|---|---|
| Redis 主节点挂掉 | docker stop | 是否全链路不可用、扣减记录丢多少 |
| MQ 不可用 | docker stop broker | 已返回"抢到"但没落库的有多少 |
| 消费者卡死 | 消费线程 sleep 60s | 堆积多久追平 |
| 数据库慢查询 | 加一条无索引 SQL | 入口 RT 是否被拖慢（应该不会） |

**当天验收**：一张 4 行的表。**这张表是简历上唯一抄不来的内容**——它只能来自真的跑过。

**开工前（2026-11-04，未开始）**

- **是 5 行不是 4 行**：需求书点名的「**磁盘近满**」要补回来（容器内 `fallocate` 填到 96%，看先坏的是 Redis AOF 还是 MySQL binlog）。做不出来就在报告里写"未验证"，不要换别的充数。
- **"Redis 故障"不能写成"删 key"一行，要按 key 分三行**：

  | 删掉的 key | 症状 |
  |---|---|
  | `quota:stock:*` | 立刻有 `STOCK_CACHE_MISSING(9005)` |
  | `quota:meta:*` | **完全没有症状**——`ResourceMetaCache` 静默回源，只多一次 DB 读 |
  | `quota:roster:*` | 才有 `NOT_ELIGIBLE(1005)`；1005 不是 1004（1004 = `RESOURCE_NOT_OPEN`） |

  只删 `meta` 去验"删 Redis 不影响主链路"，会得到**假阴性**。造 1005 要复用 r2（`quota_college` 有 4 行，需改 `close_at` + 种 roster/college key）。
- 五条操作纪律（D8 收尾踩出来的，D10 会反复用）：
  1. **改消费组属性前先存全字段基线**——`updateSubGroup` 是**覆盖式**的，没传的字段会被重置（`consumeBroadcastEnable` 就从 true 被打成 false）。存档 → 改 → 再取 → 逐字段 diff。
  2. **`cg_record` 不许 `-m false`**——它的语义是"无位点时从 max 起"，对落库链路等于**静默跳过积压 = 少数据**；`true` 只是多写一遍，唯一键挡得住。要干净起点就新建 `quota_claimed_bench`，不动主 Topic。
  3. **启动必须让日志落盘**——`dev-server.ps1 up` 起的进程会被回收（两个服务都打了 `Tomcat started` 然后消失，`err.log` 为空）。用工具托管 + `>> logs/app.log 2>&1`。
  4. **停服按端口取 owner**，不要只看 pid 文件（经常 stale）。
  5. **`INSERT IGNORE` 的坑**——`docker exec sh -c '... -p {json}'` 会吃掉双引号 → `poison=1`，差点记成"重复被正确丢弃"。用 `-e PAYLOAD="$JSON"` 走环境变量。`poison` 与"唯一键挡掉"是两个完全不同的 result。

## 5. 每天的最低纪律

1. **每天必须有 commit**，当天跑不通的代码也要提交到分支，不要留在本地
2. **每组实验必须有对照组**，不允许只记录优化后的数据
3. **失败数据不许删**。并发加到某个值后吞吐反而下降，这是最重要的发现，要写进报告而不是抹掉
4. **时间盒**：环境 1 天、前端半天、Docker 起 RocketMQ 半天。超时就降级，不死磕
5. **（2026-11-04 补）报任何容量数字，必须同时报窗口长度与两侧预热状态**。缺一项，这个数就不可比
6. **（2026-11-04 补）"没验证"不许写成"已验证"**。`minRemain`、补偿计数器、`deliveryAttempt<=1`
   都是代码写完但没注入验证过的，报告里只能写"代码已实现、未实测"
