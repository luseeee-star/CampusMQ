## 0. 开始前必须定死的三件事

### 0.1 范围：砍掉一切不产生数据的部分

| 砍掉 | 替代方案 |

| 前端页面 | 一个最简 HTML + curl 脚本，时间盒 **半天**，D11 做 |

| 微服务拆分 | 单体，部署 2 个实例即可 |
| K8s | docker-compose |

不做这些不是偷懒：**它们不产生任何并发数据，占用的是你最缺的时间。**

**执行后（2026-11-04）**：这张表基本照做，两处偏离——
① 通知不只是"写表"，做成了写表 + 退避重试（SYS-2 要求"失败可重试"，只写表不满足）；
② 前端在 D11 直接砍掉（§3 第一砍），管理端接口保留。

### 0.2 环境：时间盒 1 天，超时就降级

| 组件 | 方案 | 降级方案（装不上就用这个） |
|---|---|---|
| Redis 7 | Docker | 本机装 Windows 版 |
| RocketMQ 5.x | Docker（broker + proxy 两个容器） | **降级为 Redis List 做队列**，先跑通链路，D3 再换回来 |
| MySQL 8 | Docker 或本机 | 本机 |
| 压测 | Gatling 独立容器 | JMeter |

**Docker 起 RocketMQ 是最可能卡住的地方。** 卡超过半天就直接降级，不要死磕——队列用什么是次要的，链路跑通才是主要的。

**执行后（2026-11-04）**：RocketMQ 5.x **没有降级**，broker + proxy + dashboard 五容器起来了。
但踩了两个环境坑，都写进了 README：
- D 盘常驻 90%，触发 Broker 的 75/85/90 三道磁盘闸，所有写入被拒成 50001 → store 挪到 C 盘；
  后来 `diskMaxUsedSpaceRatio` 从 88 抬到 95。**所以 D10 的磁盘实验要填到 96% 才会触发拒写。**
- Docker 冷启动时 store 里的 `abort` 文件会触发异常恢复，worker 挂 → 队列满 → main 永久阻塞。
**压测工具没有用 Gatling**，原因见 §4（结论：自研 hammer 反而拿到了 Gatling 拿不到的判据）。

### 0.3 压测机：一台电脑也要做隔离

学生只有一台电脑，压测端和被测端在同一台机器上，数据会有偏差。务实的做法：

```
Docker 限制应用容器 CPU：--cpus=2
Gatling 跑在另一个容器，限制 --cpus=2
这样至少 CPU 是隔离的，RT 数据可用作相对对照
```

**务必在报告里注明"本机压测，数据用于相对对照，非绝对容量"。** 这句话写进 README，面试时主动说出来，比被人问出来强。

**执行后（2026-11-04）**：**没有做 `--cpus` 隔离**。应用直接 `java -jar` 裸跑在 Windows 上，
和压测器共用 32 核。所以报告里"容量"只能讲相对对照，绝对值换机器不成立。
代价要主动说：`1.33ms/fsync` 是 WSL2 + Docker Desktop 的产物，323 条/s 这个绝对值出不了这台机器，
但"减少 fsync 次数带来 3.4x"与平台无关。

## 2. 逐日明细

每节保留原计划的"怎么做"，末尾追加 **实测 / 修正**——那是实际跑出来之后与计划不同的部分。

### D1 · 裸数据库版：先亲眼看见超卖

不要一上来就上 Redis。**先做一个必定超卖的版本，把它测出来**——这是后面所有设计的对照组，也是简历上最有说服力的一组数据。

```
1. MySQL 建两张表：activity（总名额、余量）、slot_record（学号 + 活动ID 唯一索引）
2. 写一个接口：SELECT 余量 → 判断 > 0 → UPDATE 余量 -1 → INSERT 记录
3. 用 Gatling 打 200 并发，名额设 200
4. 记录：成功数、超卖数、RT
```

**当天验收**：超卖数 > 0，截图保存。这句"裸 DB 版本在 200 并发下超卖 37 件"就是简历上第一句话的由来。

**实测 / 修正（2026-10-27）**

- **不能建在 `activity` / `slot_record` 上**。主 schema 有 `CHECK (remain >= 0)`，裸版"先读后改"
  并发下 remain 会掉到 −1，MySQL 直接抛 CHECK violation——**拿到的是异常，不是"超卖 37 件"这个数据**。
  改用独立的 `bare_activity` / `bare_slot_record`：无 CHECK、无唯一索引。
- 压测器不是 Gatling，是 `benchmark/hammer/BaselineHammer.java`（JDK 21 单文件，零依赖）。
- 实测 **超卖 65–86 件**（3 轮：86 / 71 / 65），吞吐 370 req/s。
- **两个必须固定的实验条件**：压测加 `--spring.profiles.active=bench`（SQL 日志开着时超卖只有 54–67 件，
  日志在持连接期间打印，压低了有效并发，把 bug 藏起来一半）；每轮同时 reset Redis 与 DB。
- 判据只有一条：**`remain < 0`**，超卖件数 = `−remain`。
  原稿"三个数互不相等"是把一对必然相等的量当成了独立校验（`records == consumed` 恒等）。
- 副产品：800 并发时裸版先崩在 Hikari 连接池（45 个 9001），**再是超卖**——裸版有两道墙。

### D2 · Redis Lua：让超卖归 0

```lua
-- KEYS[1]=余量key  KEYS[2]=已抢集合  ARGV[1]=学号
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[1]))
if s == nil or s <= 0 then return 0 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

返回值语义定死：**1 抢到 / 0 已满 / -1 已参与**。这个约定后面所有代码都依赖它，不要改。

**当天验收**：同样 200 并发，超卖数 = 0，连跑 5 轮。

**实测 / 修正（2026-10-27）**

- 上面这段是**对照版本**，落地为 `claim_basic.lua`，返回码多一个 **−2 = 库存 key 缺失**
  （删 key 的实验要有专门症状，不能和"已满"混）。最终版 `claim.lua` 留到 D4 启用——
  把 D4 的能力提前塞进对照组，两组差异就被混在一起了。
- 实测 200 并发 × 3 = 600 请求，容量 200：**5 轮全 200 成功、超卖 0、drift 0**。
- **"Redis 让吞吐变快"是错的**：D2 317 req/s 比 D1 385 还慢 18%。Redis 挡的是超卖，
  吞吐跃升全来自 D3 的 MQ 异步（D2→D3 10.6 倍，同 JVM 同窗口）。
- 所以 D2 的验收口径改成**只验正确性**，吞吐归 D3。原口径会把"换判定方"当成"换执行方式"。

### D3 · MQ 异步落库：把落库移出用户等待

```
扣减成功 → 发消息 → 立即返回
消费者：幂等 INSERT（唯一索引兜底）+ 数据库余量 -1（同事务）
```

**当天验收**：入口 RT 从 D1 的多少降到多少（记录在案）。这是"异步化降低 RT"的直接证据。

**实测 / 修正（2026-10-27）**

- 吞吐 **364 → 490 req/s（+35%）**，p99 1269 → 970ms，**p50 降 61%** 才是主要收益——
  尾部延迟的瓶颈从数据库换到了 MQ 发送侧。
- **异步化没消灭往返，只换了往返**。同步发一条 MQ 和同步写两次库，对请求线程是同一种等待。
  数量级提升只有批量落库或去掉框架锁（后者在 D7 兑现，×2.27），不是"换个拓扑"。
- **第一轮永远丢弃**：同 jar 同参数，首轮 336、后三轮 505–515，差 50% 来自 JIT/连接池/缓存冷启动。
- **账平看 `pending` 不看 `records`**：异步之后压测结束那一刻 `records` 一定比成功数少，
  必须 `/drain` 等它归 0。`pending < 0` 不是超卖，是"投递超时但消息其实进了 Broker"的模糊态，归 D9。
- 真 `kill` 消费者再压 200 请求：`pending=200 / records=0`，重启后自动追平，无人工干预。
- **幂等命中的重放分支绝对不能发消息**：发了会让消费端判定"重复"→ 回补余量 →
  明明没扣却多出一个名额。压测器每次用新学号，永远测不到它。

### D4 · 幂等：重复请求返回首次结果

需求 R-3 的要求，也是最容易写错的一条。**不要只做"拦截重复"，要做"返回首次结果"**：

```
requestId → 缓存首次响应（含结果、订单号），TTL 60s
重复请求直接返回这份缓存
```

**当天验收**：同一学号提交 3 次，三次响应体完全一致（不是"你已参与过"）。

**实测 / 修正（2026-10-27）**

- **TTL 从 60s 改掉**，而且两条链路不一样（故意差 47 倍）：同步 `/api/claim` 是
  `confirm_timeout + 600`（实测 2,400s）；异步 `/api/claim/mq` 是
  `max(confirmTimeout+600, close_at − now + 1天)`（实测 680,909s ≈ 7.9 天）。
  60s 甚至 40 分钟都活不过一场跨天活动——重复点击会变成一次全新申领（多扣一次 Redis 但没有记录，`pending` 永久为正）。
- **响应体是合同，可观测性走响应头**：加了 `X-Claim-Replay: 1`，不塞 body。
  塞 body 会让前端显示"你已申领过"，正好是需求书反对的交互。
- 学院配额顺手做完，但**默认关闭**（`campusslot.claim.college-quota-enabled=false`）：
  4 院 × 20 打满 80，第 21 人返回 **2002** 而不是 2001，全场仍有剩余——两个码不能混，这是 R-8 的硬要求。

### D5 · 压测基线：找出拐点（最关键的一天）

阶跃加压：500 → 1000 → 2000 → 4000 → 6000 → 8000 QPS，每档持续 60 秒。记录每档的：

| 记录项 | 用途 |
|---|---|
| 吞吐（实际完成 QPS） | 画饱和曲线 |
| P50 / P99 RT | 画恶化曲线 |
| 失败率 | 找可用性边界 |
| Redis CPU | 判断是否到 Redis 上限 |

**当天验收**：一张表 + 一条结论："单 key 判定在 X 万 QPS 出现拐点，P99 从 A ms 涨到 B ms"。**这张表是整个项目最值钱的东西。**

同时补跑分层对照（D1/D2/D3 三个版本各压一遍），回答"每一层到底挡住了多少"。

**实测 / 修正（2026-10-28～29，用了 2 天）**

- **加压方式改了**：不是"固定 QPS 每档 60 秒"，而是 `--sweep` 闭合环扫并发（100/200/400/800，5s/20s 窗口）
  + `--qps` 开环（500→8000）互证。原因：60 秒窗口会被消费侧的 323 条/s 拖成积压，
  测出来的不是入口容量。**最终 5 秒窗口没问题，问题在预热状态。**
- **4500 这个"压测器上限"是自己推错的**（固定次数模式标的）。换 sweep 后同一端点 45.6k @200 并发，
  差 10 倍。**压测器不是瓶颈，业务链路 3.85k 只占它 8%。**
- **拐点 200**，200 之后吞吐平坦（±1%），摘锁前后形状不变、高度变了：

| 口径 | 数值 | 说明 |
|---|---|---|
| 单 key Lua（带框架锁） | 6,749 / 6,649 | 400 档，两侧预热到位 |
| 探针摘锁 `/claim-sha` | **27,807** | ×4.47；Redis 0.83 核、Lettuce 0.89 核 |
| 主链路摘锁（EVALSHA） | 11,356 | ×2.27 vs 持锁 5,006（ABAB，噪声 <2%） |
| 端到端（含 MQ） | **3,845 / 3,868** | 开环与闭合环差 0.6%，瓶颈是消费侧 323 条/s |

- **NFR 对账改判**：NFR-1 只有 ≤3000 档达标（3000 热档 P99=145ms，贴线），4000 起断裂；
  NFR-2 在 12/12 档 + 开环 8/8 全 0%；**NFR-6 不达标**——入口 11.3k 够，端到端 3.85k 差 2.08 倍。
- **冷启动是第一档的毒药**：2000 档冷跑 P99 1,189ms vs 热跑 18ms（66 倍）；4000 档冷跑 rej 17~19%、热跑 0。
- **报容量必须同时说三件事**：窗口长度、客户端是否预热、服务端是否预热。同一个数在三种状态下是
  4,188 / 5,541 / 6,746——不标状态等于没报。

### D6 · 网关限流：阈值从 D5 反推

```
阈值 = D5 实测容量 × 0.7 ÷ 实例数
```

用 Sentinel 或 Spring Cloud Gateway 内置限流器都行，重点是**阈值必须有出处**，不能拍脑袋。

**当天验收**：压到容量的 3 倍，放行量稳定在阈值附近，被拒请求 RT < 5ms。

**实测 / 修正（2026-10-29）**

- **阈值不是"容量 × 0.7"**。取的是 **3000**——D5 开环实测 3000 档 P99=145ms、处理能力仍占输入 98%，
  4000 档掉到 76% 并越过 200ms。闸门设在"最后一个还舒服的档位"，不是百分比。
- 实现：无锁 CAS 令牌桶（令牌用 **double**）+ `RateLimitFilter`（`@Order(0)`，先于身份解析，429 + 3001）
  + Prometheus 两个指标。默认 `enabled=false`——D5 基线都在无限流下测的。

| 段 | 设置 | 结果 |
|---|---|---|
| 不误伤 | 限额 3000、到达 2996/s | 放行 14,332，**服务端拒绝 0** |
| 钉住 | 限额 1000、到达 2991/s | 放行 **1,027/s**（+2.7%，桶初始满）、拒绝 9,758 |
| 拒绝 RT | 限额 1、到达 1996/s | 拒绝 99.95%，服务端判定 **1.86μs**，P50 1ms / P99 6ms |

- **"拒绝 RT < 5ms"要拆两个口径**：服务端 1.86μs；端到端 P99 6ms 是压测器节拍器下限
  （每 tick 最多 park 2ms，醒来批量投递）。**不要拿端到端 P99 判限流器超时。**
- 令牌桶限的是**通过速率**不是**发起速率**。到达 6000 却拒绝 0，是客户端排队把突发摊成了 2.9k/s。
  测限流要让补充速率远低于到达速率（取 1:3）。
- 定点数令牌少放行 19%：相邻 CAS 间隔 < 1μs 时 `elapsed × rate` 不足 1 被丢成 0，而 `lastNanos` 照推。
- **待办**：qps=3000 是单 key 时代的数，D7 后主链路 11.3k、D10 还会抬消费侧。
  **不重定，"容量 11.3k"和"线上 3000 就拒"会自相矛盾。**

### D7 · 库存分片：越过单 key 上限（最难的一天，也是最大亮点）

D5 测出单 key 到顶之后，这一天做唯一超出教程范围的部分：

```
stock:{activityId}:shard:{0..15}     16 个分片
路由：hash(学号) % 16
分片为空则随机换一个分片重试（最多 2 次）
对账时按 16 个分片求和
```

**当天验收**：再压一遍，对比 D5 —— 吞吐提升多少、P99 降多少。

**必须想清楚并写进 README 的问题**：某个分片卖完、别的还有，怎么处理？答：允许短期不均，靠活动结束后统一结算；分片数越大，不均的绝对值越小。

> 这天做不出来就跳过，直接进 D8。**但要在 README 里写明"单 key 到 X 万 QPS 触及上限，分片方案已设计未实现"**——如实说明比假装做过好。

**实测 / 修正（2026-11-02～03，结论是"不做"）**

三条判据全不成立，再加一条结构约束：

| 判据 | 实测 | 结论 |
|---|---|---|
| Redis 是否到顶 | INFO cpu 10s 窗口：user 1.72s + sys 2.32s = **单核 40.4%**（sys 高于 user，一半 CPU 在 socket I/O） | 没到顶 |
| 是否有热点 key | 400 并发时"周期 − RT"缺口 <1ms | 单 key 无热点 |
| 能否按 key 拆 | `claim.lua` 一次 EVAL 碰 stock/meta/roster/college 三类以上 key，Cluster 下 **CROSSSLOT**；加 hash tag 退化成单槽 | **结构上做不到** |

真正的产出是"证伪一个数字 + 找到一个限速器"：

- `jstack`：400 个 Tomcat 线程里 392 WAITING，**393 个卡在 `DefaultRedisScript.getSha1()`
  的 JVM 全局锁**上（即使 SHA1 已缓存）。**6.7k 是这把锁的容量，不是链路容量。**
- 判决实验（`/claim` vs `/claim-sha`，同端点 ABAB）：5,669 → **25,357（×4.47）**。
- 天花板重测：27k 时 app 7.6 核 / Redis 0.83 核 / **Lettuce event loop 0.89 核（89%）**，
  全机 CPU 只用 42.6%。外推 Lettuce 100% ≈ 30.3k，**先撞的是 event loop，不是 Redis**。
- 分片收益上限 **+12%**（只摊平 Redis），而 D8 阶段 0 已把主链路切 EVALSHA，
  锁拿掉后容量 11.3k——**分片彻底没有理由了。**
- 上面那段"分片卖完怎么办"的设计保留作为思考记录，但**实现状态是未实现**，README 要如实写。
- 负结果本身要进报告：**"量了三个判据，结论是不做"比"做了分片"更能说明判断力。**

### D8 · 超时释放 + 补位队列

- 用 RocketMQ 延迟消息（或 Redis ZSET 到期扫描）实现 30 分钟释放
- 取消必须 `SREM` 判返回值（漏判会导致余量虚增）
- 释放的名额进补位队列，不重新开放抢号（需求 R-6）

**当天验收**：投放 1000 个不同到期时刻的锁定，释放误差 P99 < 1s；同一学号取消 10 次，余量只回补 1 次。

**实测 / 修正（2026-11-03～04，用了 2 天；标题里的"补位"没做）**

- **释放走扫表，不走延迟消息**。`quota_release_delay` 至今**没有生产发送点**，
  `sendDelay` 只被 `DevMqController` 烟测调用。当前唯一释放路径是
  `@Scheduled(fixedDelay=500ms)` + `LIMIT 100` + 逐条 800ms 预算 + 单条一个事务。
  用 `fixedDelay` 不是 `fixedRate`：后者在积压期会把执行间隙压到 0，吃满调度池一根线程，
  同池的 SYS-2 重试只能抢剩下那根。调度池 `pool.size: 2`。
- **取消不是 `SREM`**，是 DB 复合条件 UPDATE 判受影响行数（`releaseByStudent`），
  DB 提交后再 `release.lua` INCR。顺序反过来在 DB 失败时会让余量虚增且没有第二次机会扣回。
- **"同一学号取消 10 次只回补 1 次"**：靠 `WHERE status='LOCKED'` 条件更新 + 保留幂等键实现。
  **取消时绝不删 Redis 幂等键**——删了学生再点会走完整扣减并投消息，
  消费端撞唯一索引 → ACK 不回补 → **少发**（唯一索引挡住同一个人拿两次，所以不是超发）。
- **释放误差 P99 改双口径**：稳态 P99≈0.5s（500ms 周期决定）；积压期结构下限 1.3s
  （800ms 预算 + 500ms 间隔），换实现也没用。秒精度下这个 P99 根本不可证，
  `quota_record` 6 个时间列已全升 `DATETIME(3)`（亚秒边界实测：`expire_at=43.589` / `now=43.234` 同秒确认成功）。
- **补位未做**（R-6 直接违反）。原因：取消后不可重抢 + 补位需要独立队列和二次筛选，时间不够，
  收益低于 D9/D10。**README 必须写明"设计上违反 R-6"，不能只在计划里标"没做"。**
- 实测吞吐：释放一条 9.4–13ms（学院路径 22–26ms），单实例追平 **~65 条/s**。
  **NFR-5 的"<1s"只能是稳态口径**，到期速率 = 抢号速率 ×(1−确认率)，大促下必然被击穿，
  报告要写清这是**设计前提**不是 bug。
- SYS-2 通知：写表 + `next_retry_at` 7 次 × 1s 起（1/2/4/8/16/32 = 63s），
  第 7 次失败同轮置 DEAD，实测端到端 **64.3s**（63s + 累计 tick 1.3s）。
  锁定通知走 `cg_notify` 消费 `quota_claimed`，实测 `/api/claim/mq` → 位点 +1 → `lock:3:S9Z2` SENT/1，约 2s。
  **`/api/claim` 是同步落库、不发 MQ**，用它会得到"链路不通"的假结论——两个入口不能混。
- **通知覆盖率的分母必须带时间下界**（`deploy/sql/report.sql` 的 `@t0`），
  否则 r3 是 3/16 = 19% 的假红灯；且 lock 覆盖率只对 `/api/claim/mq` 入口成立。

### D10 · 故障注入：做出故障矩阵（第二关键的一天）

对每个故障，记录三件事：**用户看到什么 / 损失多大 / 多久恢复**。

| 故障 | 注入方式 | 要观察的 |
|---|---|---|
| Redis 主节点挂掉 | docker stop | 是否全链路不可用、扣减记录丢多少 |
| MQ 不可用 | docker stop broker | 已返回"抢到"但没落库的有多少 |
| 消费者卡死 | 消费线程 sleep 60s | 堆积多久追平 |
| 数据库慢查询 | 加一条无索引 SQL | 入口 RT 是否被拖慢（应该不会） |

**当天验收**：一张 4 行的表。**这张表是简历上唯一抄不来的内容**——它只能来自真的跑过。

**修正（2026-11-04，尚未开始）**

- **是 5 行不是 4 行**：需求书点名的「**磁盘近满**」要补回来（容器内 `fallocate` 填到 96%，
  看先坏的是 Redis AOF 还是 MySQL binlog）。做不出来就在报告里写"未验证"，不要换别的充数。
- **"Redis 故障"不能写成"删 Redis key"一行，要按 key 分三行**：

  | 删掉的 key | 症状 |
  |---|---|
  | `quota:stock:*` | 立刻有 `STOCK_CACHE_MISSING(9005)` |
  | `quota:meta:*` | **完全没有症状**——`ResourceMetaCache` 静默回源，只多一次 DB 读 |
  | `quota:roster:*` | 才有 `NOT_ELIGIBLE(1005)` |

  当前 `quota:meta:*` 本来就不在 Redis 里（全靠回源），只删 meta 去验"删 Redis 不影响主链路"，
  会得到一个**假阴性**。1005 不是 1004（1004 = `RESOURCE_NOT_OPEN`），造场景要复用 r2
  （`quota_college` 有 4 行，需改 `close_at` + 种 roster/college key）。
- 五个操作纪律（D8 收尾踩出来的，D10 会反复用）：
  1. **改消费组属性前先存全字段基线**。`mqadmin updateSubGroup` 是**覆盖式**的，没显式传的字段会被重置
     （`consumeBroadcastEnable` 就被从 true 打成 false）。流程：存档 → 改 → 再取 → 逐字段 diff。
  2. **`cg_record` 不许 `-m false`**。它的语义是"无位点时从 max 起"，对落库链路 = **静默跳过积压 = 少数据**；
     `true` 只是"多写一遍"，唯一键挡得住。落库链路取 at-least-once。
     真要干净起点，新建 `quota_claimed_bench` 专供 D10，不动主 Topic。
  3. **启动必须让日志落盘**。`dev-server.ps1 up` 起的进程会被回收（两个服务都打印了 `Tomcat started`
     然后消失，`err.log` 为空）。可用方式：工具托管 + `>> logs/app.log 2>&1`。
  4. **停服按端口取 owner**，不要只看 pid 文件（经常 stale）。
  5. **`INSERT IGNORE` 的坑**：手工重投测试时用 `docker exec sh -c '... -p {json}'` 会吃掉双引号 →
     `poison=1`，差点记成"重复被正确丢弃"。用 `-e PAYLOAD="$JSON"` 走环境变量。
     `poison` 与"唯一键挡掉"是两个完全不同的 result。

### D13 · 压测报告 + README

## 5. 每天的最低纪律

1. **每天必须有 commit**，当天跑不通的代码也要提交到分支，不要留在本地
2. **每组实验必须有对照组**，不允许只记录优化后的数据
3. **失败数据不许删**。并发加到某个值后吞吐反而下降，这是最重要的发现，要写进报告而不是抹掉
4. **时间盒**：环境 1 天、前端半天、Docker 起 RocketMQ 半天。超时就降级，不死磕
5. **（2026-11-04 补）报任何容量数字，必须同时报窗口长度与两侧预热状态**。缺一项，这个数就不可比
6. **（2026-11-04 补）"没验证"不许写成"已验证"**。`minRemain`、补偿计数器、`deliveryAttempt<=1`
   都是代码写完但没注入验证过的，报告里只能写"代码已实现、未实测"
