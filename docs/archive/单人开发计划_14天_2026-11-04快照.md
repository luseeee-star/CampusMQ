## 0. 开始前必须定死的三件事

### 0.1 范围：砍掉一切不产生数据的部分

| 砍掉 | 替代方案 |
|---|---|
| 前端页面 | 一个最简 HTML + curl 脚本，时间盒 **半天**，D11 做 |
| 管理端界面 | 只做 2 个 HTTP 接口（建活动、导对账），不做页面 |
| 登录 / 鉴权 | 学号从请求参数传入，不接统一身份认证 |
| 真实通知 | 打日志 + 写通知表，不接短信 / 企微 |
| 微服务拆分 | 单体，部署 2 个实例即可 |
| K8s | docker-compose |

不做这些不是偷懒：**它们不产生任何并发数据，占用的是你最缺的时间。**

**执行后（2026-11-04）**：这张表基本照做，两处偏离——
① 通知不只是"写表"，做成了写表 + 退避重试（SYS-2 要求"失败可重试"，只写表不满足）；
② 前端在 D11 直接砍掉（§3 第一砍），管理端接口保留。

### 0.2 环境：时间盒 1 天，超时就降级

| 组件 | 方案 | 降级方案（装不上就用这个） |
|---|---|---|
| Redis 7 | Docker | 本机装 Windows 版 |
| RocketMQ 5.x | Docker（broker + proxy 两个容器） | **降级为 Redis List 做队列**，先跑通链路，D3 再换回来 |
| MySQL 8 | Docker 或本机 | 本机 |
| 压测 | Gatling 独立容器 | JMeter |

**Docker 起 RocketMQ 是最可能卡住的地方。** 卡超过半天就直接降级，不要死磕——队列用什么是次要的，链路跑通才是主要的。

**执行后（2026-11-04）**：RocketMQ 5.x **没有降级**，broker + proxy + dashboard 五容器起来了。
但踩了两个环境坑，都写进了 README：
- D 盘常驻 90%，触发 Broker 的 75/85/90 三道磁盘闸，所有写入被拒成 50001 → store 挪到 C 盘；
  后来 `diskMaxUsedSpaceRatio` 从 88 抬到 95。**所以 D10 的磁盘实验要填到 96% 才会触发拒写。**
- Docker 冷启动时 store 里的 `abort` 文件会触发异常恢复，worker 挂 → 队列满 → main 永久阻塞。
**压测工具没有用 Gatling**，原因见 §4（结论：自研 hammer 反而拿到了 Gatling 拿不到的判据）。

### 0.3 压测机：一台电脑也要做隔离

学生只有一台电脑，压测端和被测端在同一台机器上，数据会有偏差。务实的做法：

```
Docker 限制应用容器 CPU：--cpus=2
Gatling 跑在另一个容器，限制 --cpus=2
这样至少 CPU 是隔离的，RT 数据可用作相对对照
```

**务必在报告里注明"本机压测，数据用于相对对照，非绝对容量"。** 这句话写进 README，面试时主动说出来，比被人问出来强。

**执行后（2026-11-04）**：**没有做 `--cpus` 隔离**。应用直接 `java -jar` 裸跑在 Windows 上，
和压测器共用 32 核。所以报告里"容量"只能讲相对对照，绝对值换机器不成立。
代价要主动说：`1.33ms/fsync` 是 WSL2 + Docker Desktop 的产物，323 条/s 这个绝对值出不了这台机器，
但"减少 fsync 次数带来 3.4x"与平台无关。

## 2. 逐日明细

每节保留原计划的"怎么做"。已开工的节末尾追加 **落地**，未开工的追加 **开工前**——
两者都只写三件事：**实现了什么 / 哪点没实现 / 为什么改原方案**。
实测数据、踩坑过程留在 `LOGBOOK.md`，这里不复述。

### D1 · 裸数据库版：先亲眼看见超卖

不要一上来就上 Redis。**先做一个必定超卖的版本，把它测出来**——这是后面所有设计的对照组，也是简历上最有说服力的一组数据。

```
1. MySQL 建两张表：activity（总名额、余量）、slot_record（学号 + 活动ID 唯一索引）
2. 写一个接口：SELECT 余量 → 判断 > 0 → UPDATE 余量 -1 → INSERT 记录
3. 用 Gatling 打 200 并发，名额设 200
4. 记录：成功数、超卖数、RT
```

**当天验收**：超卖数 > 0，截图保存。这句"裸 DB 版本在 200 并发下超卖 37 件"就是简历上第一句话的由来。

**落地（2026-10-27）**

- 实现：200 并发、共 600 次请求，三轮分别超卖 **86 / 71 / 65 件**，每秒处理 370 次，对照组数据到手。
- 未实现：无。但建不到原计划说的 `activity` / `slot_record` 两张表上——主库给余量加了"不能小于 0"的约束，并发下会直接报错，拿到的是异常而不是超卖数；改成另建两张什么约束都没有的 `bare_*` 表。
- 改动：压测工具从 Gatling 换成一个 Java 文件 `benchmark/hammer/BaselineHammer.java`，直接跑。原因：这天只要数一数成功、失败、超卖各多少，搭容器的成本换不来东西，Gatling 留到 D5。另外压测必须关掉 SQL 日志，否则日志拖慢执行，超卖会从 86 缩到 54–67 件，把问题藏掉一半。
- 改动：判定标准从"三个数互不相等"改成只看"余量有没有变成负数"。原因：记录数本来就等于扣减数，原写法把一对必然相等的数当成了两个独立验证。

### D2 · Redis Lua：让超卖归 0

```lua
-- KEYS[1]=余量key  KEYS[2]=已抢集合  ARGV[1]=学号
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end
local s = tonumber(redis.call('GET', KEYS[1]))
if s == nil or s <= 0 then return 0 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

返回值语义定死：**1 抢到 / 0 已满 / -1 已参与**。这个约定后面所有代码都依赖它，不要改。

**当天验收**：同样 200 并发，超卖数 = 0，连跑 5 轮。

**落地（2026-10-27）**

- 实现：200 并发连跑五轮全部正常，**超卖 0**，账面也没有差。脚本落地为 `claim_basic.lua`，返回值多加了一个 **−2 表示"库存数据不存在"**（后面要做删数据的故障实验，得有自己专门的症状，不能和"已经抢完"混在一起）。
- 未实现：无。
- 改动：验收标准从"既看正确性又看速度"改成**只看正确性**。原因：实测每秒 317 次，比 D1 的 385 还**慢了 18%**——换成 Redis 只是把"谁来判定"挪了个位置，写库的两次往返一次没省。速度的提升实际发生在 D3。
- 改动：完整版的 `claim.lua` 推迟到 D4 才启用。原因：如果提前把防重复、学院配额塞进对照组，两组之间的差异就说不清是谁带来的。

### D3 · MQ 异步落库：把落库移出用户等待

```
扣减成功 → 发消息 → 立即返回
消费者：幂等 INSERT（唯一索引兜底）+ 数据库余量 -1（同事务）
```

**当天验收**：入口 RT 从 D1 的多少降到多少（记录在案）。这是"异步化降低 RT"的直接证据。

**落地（2026-10-27）**

- 实现：每秒从 364 提到 **490 次**（涨 35%），一半请求的耗时降了 61%；手动停掉消费者再压 200 次请求，重启后自己追平了。
- 未实现：无。
- 改动：结论改了，从"异步能带来数量级提升"改成**"异步只是把等待挪了个地方"**。原因：发一条消息和写一次库，对请求线程来说是同一种等待。真正的数量级提升来自 D7 去掉的那把锁（2.27 倍）。
- 改动：账对不对的判断，从"记录数等于成功数"改成"等排队数归零"。原因：改成异步之后，压测刚结束那一刻记录必然还差几条，按原标准会误判成丢消息。另外第一轮的数据要丢掉：后三轮是 505–515，第一轮只有 336，差的 50% 是刚启动时各种缓存还没热。

### D4 · 幂等：重复请求返回首次结果

需求 R-3 的要求，也是最容易写错的一条。**不要只做"拦截重复"，要做"返回首次结果"**：

```
requestId → 缓存首次响应（含结果、订单号），TTL 60s
重复请求直接返回这份缓存
```

**当天验收**：同一学号提交 3 次，三次响应体完全一致（不是"你已参与过"）。

**落地（2026-10-27）**

- 实现：同一个学号提交三次，三次返回的内容一字不差；是不是重复请求，靠响应头 `X-Claim-Replay: 1` 告诉调用方。学院配额的分支顺手做完了，默认关着。
- 未实现：无。
- 改动：结果缓存的保存时长从 60 秒改掉，两条链路分别按活动情况算：同步入口 40 分钟，异步入口约 7.9 天（差 47 倍是故意的）。原因：60 秒根本活不过一场跨天的活动，学生过一会儿再点，会被当成一次全新的申领——Redis 里多扣了一个名额，数据库却没有对应记录，这个差额永远平不了。
- 改动：首次结果只放在响应头里，不写进返回内容。原因：写进去前端就会提示"你已申领过"，而需求要的正是别这么提示。

### D5 · 压测基线：找出拐点（最关键的一天）

阶跃加压：500 → 1000 → 2000 → 4000 → 6000 → 8000 QPS，每档持续 60 秒。记录每档的：

| 记录项 | 用途 |
|---|---|
| 吞吐（实际完成 QPS） | 画饱和曲线 |
| P50 / P99 RT | 画恶化曲线 |
| 失败率 | 找可用性边界 |
| Redis CPU | 判断是否到 Redis 上限 |

**当天验收**：一张表 + 一条结论："单 key 判定在 X 万 QPS 出现拐点，P99 从 A ms 涨到 B ms"。**这张表是整个项目最值钱的东西。**

同时补跑分层对照（D1/D2/D3 三个版本各压一遍），回答"每一层到底挡住了多少"。

**落地（2026-10-28～29，用了 2 天）**

- 实现：**200 并发处出现拐点**，之后再加并发吞吐基本不动（±1%）。同一套系统量出四个数：带锁 6,700、去掉锁的探针 27,800、主链路去掉锁 11,300、端到端 3,850。
- 未实现：无。但原定一天不够——拐点只是一条曲线，三项指标的对账、三层对照、定量投递的验证各要另跑一套。
- 改动：加压方式从"每档固定压力跑 60 秒"改成"逐步加并发 + 定量投递，两种方式互相印证"。原因：跑 60 秒的窗口里，消费端每秒只处得了 323 条，积压会把入口的容量盖住，量到的就不是入口能力了。
- 改动：核心数字从"单 key 的拐点"改成**"曲线形状 + 三个数并列"**。原因：4,007 是**带锁**时量的——400 个请求线程里有 393 个卡在同一把 Java 全局锁上（`getSha1()`），6,700 是这把锁的上限，不是链路的上限。
- 改动：三项指标重新判——七成以上档位达标，**每秒 8000 那一项明确不达标**（端到端只有 3,850）。原因：原表把"计划落点"画成了"已经达标"，这是最容易被一句话问穿的地方。
- 口径：原来说的"压测工具上限 4,500"已经被推翻，同一个接口实际能打到 45,600。报容量必须同时交代三件事：跑多久、客户端热没热、服务端热没热——同一个数在三种状态下分别是 4,188 / 5,541 / 6,746。

### D6 · 网关限流：阈值从 D5 反推

```
阈值 = D5 实测容量 × 0.7 ÷ 实例数
```

用 Sentinel 或 Spring Cloud Gateway 内置限流器都行，重点是**阈值必须有出处**，不能拍脑袋。

**当天验收**：压到容量的 3 倍，放行量稳定在阈值附近，被拒请求 RT < 5ms。

**落地（2026-10-29）**

- 实现：把限额设成 1000 时，实际放行 **1,027 次/秒**（多 2.7%），该放行的场景一次都没误伤；被拒绝的请求，服务端判断只花 **1.86 微秒**。
- 未实现：无。
- 改动：阈值没有按"容量乘 0.7"算，直接定成 **3000**。原因：3000 是最后一个还舒服的档位（99% 的请求 145 毫秒内完成，能处理掉输入的 98%），到 4000 就掉到 76% 并且超过 200 毫秒。百分比那个算法没有依据。
- 改动："被拒请求 5 毫秒内返回"拆成两个数：服务端判断 1.86 微秒；端到端一半 1 毫秒、99% 6 毫秒。原因：6 毫秒是压测工具自己的调度下限（它每轮最多睡 2 毫秒才发下一批），拿它去判断限流器的快慢会得出错误结论。
- 待办：3000 是单 key 时候定的，D7 之后主链路已经到 11,300。**不重新定，"容量一万多"和"线上 3000 就拒"两句话会自相矛盾——D10 之后必须重定。**

### D7 · 库存分片：越过单 key 上限（最难的一天，也是最大亮点）

D5 测出单 key 到顶之后，这一天做唯一超出教程范围的部分：

```
stock:{activityId}:shard:{0..15}     16 个分片
路由：hash(学号) % 16
分片为空则随机换一个分片重试（最多 2 次）
对账时按 16 个分片求和
```

**当天验收**：再压一遍，对比 D5 —— 吞吐提升多少、P99 降多少。

**必须想清楚并写进 README 的问题**：某个分片卖完、别的还有，怎么处理？答：允许短期不均，靠活动结束后统一结算；分片数越大，不均的绝对值越小。

> 这天做不出来就跳过，直接进 D8。**但要在 README 里写明"单 key 到 X 万 QPS 触及上限，分片方案已设计未实现"**——如实说明比假装做过好。

**落地（2026-11-02～03，结论是"不做"）**

- 实现：**决定不做分片**。量了三条判据都不成立：Redis 只用掉单核 40%，远没到上限；400 并发下没有哪个 key 特别热（等待缺口不到 1 毫秒）；最致命的是 `claim.lua` 一次要碰三类 key，Redis 集群会直接拒绝这种跨分片的命令（报 `CROSSSLOT`），加 hash tag 又会把数据全塞回同一个分片，等于没拆。顺带找到了真正的瓶颈。
- 未实现：库存分片。不是没做完，是判定不该做。
- 改动：D7 的主题从"做分片"改成**"判断该不该做分片"**。原因：分片最多只能带来 12% 的提升（它只分摊 Redis 的压力，摊不平连接池单线程已经跑到 89%），而 D8 阶段去掉那把锁之后，主链路已经有 11,300。
- 改动：把"那把 Java 全局锁"提为主要结论。原因：400 个线程里 393 个在等它；对照实验里同一个接口去掉锁之后从 5,669 涨到 **25,357（4.47 倍）**——6,700 是这把锁的上限，不是链路的上限。
- 改动：失败结论也写进报告。原因："量了三条判据，结论是不做"比"硬做了分片"更能说明判断力。

### D8 · 超时释放 + 补位队列

- 用 RocketMQ 延迟消息（或 Redis ZSET 到期扫描）实现 30 分钟释放
- 取消必须 `SREM` 判返回值（漏判会导致余量虚增）
- 释放的名额进补位队列，不重新开放抢号（需求 R-6）

**当天验收**：投放 1000 个不同到期时刻的锁定，释放误差 P99 < 1s；同一学号取消 10 次，余量只回补 1 次。

**落地（2026-11-03～04，用了 2 天）**

- 实现：确认、取消、超时释放三条路的分支全部走通；释放的延迟稳定在 0.5 秒左右，一台机器每秒能放 65 个名额；通知连续失败 7 次后判死，实测 **64.3 秒**；锁定成功的通知 2 秒内送达。
- 未实现：**退掉的名额给排队同学，这条直接违反了需求 R-6**。原因：补位要单独建一个队列再筛一遍人，时间不够，收益也不如 D9、D10。**README 里必须写明，不能只在计划里打个"没做"。**
- 未实现：原计划的"定个闹钟到点释放"。原因：这个闹钟在代码里只有一个名字，没有任何地方真的发出去过，能用它的只有开发用的手动测试接口；现在唯一的释放方式是每半秒扫一遍数据库，一次拿 100 条，每条单独一个事务。
- 改动：取消没有按原计划"从名单上划掉名字、看划没划掉"，改成先改数据库记录——只有还处于"锁定中"的那一条才能改成功，改成功之后再回补 Redis。原因：顺序反过来，一旦数据库那步失败，名额就凭空多出来，而且没有第二次机会扣回去。**取消时也绝不删 Redis 里那条防重复的记录**，删了学生再点一次就会重新扣、重新发消息，消费端撞上唯一索引不认，于是名额少发。
- 改动：通知重试从"3 次、每次隔 5 秒"改成**从 1 秒起翻倍，最多 7 次**（1 / 2 / 4 / 8 / 16 / 32，共 63 秒），配置、代码默认值、文档四处一起改。原因：既然要求"失败可以重试"，就该一路退到小时级，而不是 15 秒就放弃。
- 改动：释放延迟改成两个数：正常情况下 0.5 秒，积压时 1.3 秒是结构上的下限；同时把 `quota_record` 的 6 个时间字段精确到毫秒。原因：只精确到秒的话，这个延迟根本没法验证。1.3 秒 = 每条 800 毫秒的预算 + 半秒的扫描间隔，换实现也一样。
- 口径：`/api/claim` 这个入口是同步写库、**不发消息**的，拿它去验通知只会得出"链路不通"的错误结论，必须用 `/api/claim/mq`。另外统计覆盖率时分母要带一个时间起点，否则会算出一个假的红灯。


**当天验收**：手动删掉数据库里 3 条记录，5 分钟内对账任务能报出"差异 3 条"。**对账是消息丢失和消费失败唯一的发现渠道，不能省。**

**开工前（2026-11-04，未开始）**

- 实现：报表的统计口径已经写好并验证过（`deploy/sql/report.sql`），里面写死了一个统计起点 `SET @t0='2026-11-04 17:27:00'`；实测三类事件的通知覆盖率都是满的：锁定 6/6、确认 3/3、超时释放 4/4。

### D10 · 故障注入：做出故障矩阵（第二关键的一天）

对每个故障，记录三件事：**用户看到什么 / 损失多大 / 多久恢复**。

| 故障 | 注入方式 | 要观察的 |
|---|---|---|
| Redis 主节点挂掉 | docker stop | 是否全链路不可用、扣减记录丢多少 |
| MQ 不可用 | docker stop broker | 已返回"抢到"但没落库的有多少 |
| 消费者卡死 | 消费线程 sleep 60s | 堆积多久追平 |
| 数据库慢查询 | 加一条无索引 SQL | 入口 RT 是否被拖慢（应该不会） |

**当天验收**：一张 4 行的表。**这张表是简历上唯一抄不来的内容**——它只能来自真的跑过。

**开工前（2026-11-04，未开始）**

- **是 5 行不是 4 行**：需求书点名的「**磁盘写满**」要补回来——把容器盘填到 96%，看先出问题的是 Redis 的写入日志还是数据库的日志文件。做不出来就在报告里写"未验证"，不要拿别的凑数。
- **"Redis 出故障"不能只写成"删一个 key"，要按删的是哪类数据分三行**：

  | 删掉的数据 | 症状 |
  |---|---|
  | `quota:stock:*` | 立刻报 `STOCK_CACHE_MISSING(9005)` |
  | `quota:meta:*` | **完全没症状**——代码会自己去数据库再读一遍，只是多一次查询 |
  | `quota:roster:*` | 才会报 `NOT_ELIGIBLE(1005)`；是 1005 不是 1004（1004 是"活动未开始"） |

  只删第三类去验"删 Redis 不影响主链路"，会得到一个假的结论。要造 1005 这个场景得复用测试环境 r2（那里有 4 行学院配额，需要改活动结束时间，再补上名单数据）。
- 五条操作纪律（D8 收尾时踩出来的，D10 会反复用到）：
  1. **改消费组配置前先存一份完整记录**——那个命令是整体覆盖的，没写到的字段会被清掉（广播开关就被从"开"改成了"关"）。流程：存档 → 改 → 再取一次 → 逐项对比。
  2. **落库这条链路不许改成"从最后开始读"**——它的意思是不管积压、直接跳到最新位置，等于静默丢掉积压的消息。改成"从头读"最多是重复写一遍，唯一索引挡得住。要干净的起点就另建一个测试用主题，不要动正式的。
  3. **启动服务时日志必须落到文件**——脚本起的进程会被系统回收（两个服务都打印了启动成功然后消失，错误日志是空的）。用工具托管，把输出重定向进文件。
  4. **停服务要按端口找进程**，不能只看记录进程号的那个文件，它经常是过期的。
  5. **插入时忽略重复的写法有个坑**——用 shell 传一段 JSON 进去，引号会被吃掉，结果记成了另一种失败，差点当成"重复被正确丢弃"。改用环境变量传。这两种结果完全不是一回事。

## 5. 每天的最低纪律

1. **每天必须有 commit**，当天跑不通的代码也要提交到分支，不要留在本地
2. **每组实验必须有对照组**，不允许只记录优化后的数据
3. **失败数据不许删**。并发加到某个值后吞吐反而下降，这是最重要的发现，要写进报告而不是抹掉
4. **时间盒**：环境 1 天、前端半天、Docker 起 RocketMQ 半天。超时就降级，不死磕
5. **（2026-11-04 补）报任何容量数字，必须同时报窗口长度与两侧预热状态**。缺一项，这个数就不可比
6. **（2026-11-04 补）"没验证"不许写成"已验证"**。`minRemain`、补偿计数器、`deliveryAttempt<=1`
   都是代码写完但没注入验证过的，报告里只能写"代码已实现、未实测"
